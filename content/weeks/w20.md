## D1 · Why LLMs hallucinate, and what actually reduces it

A **hallucination** is fluent output that isn't supported by the input or by facts. It isn't a bug in one component; it follows
from how models are trained and used:

* **The objective rewards plausibility, not truth.** Next-token training maximises likelihood of human-written text; a confident,
  well-formed but wrong continuation can score well. Rare facts seen a few times in pre-training are stored weakly and
  reconstructed from similar patterns (names, dates, citations, numbers are classic failure points).
* **Evaluation and post-training reward guessing.** If benchmarks and graders score a wrong answer and "I don't know" the same
  (both zero), a model that always guesses scores higher — so training nudges it to guess. Preference training can add
  **sycophancy** (agreeing with the user's false premise) when raters prefer agreeable answers.
* **Knowledge cut-off and distribution shift:** questions about things after training data, or about a user's private context
  the model never saw.
* **Decoding:** high temperature and sampling increase errors; long generations compound early mistakes (exposure bias).
* **Context failures:** the right information is in the prompt but ignored (long context, distractors), or retrieval returned
  the wrong passage and the model faithfully used it.

**What reduces it (and the honest limits):**

* **Grounding** — retrieval (RAG), tools (search, calculator, vehicle API) and citing the source passage; only as good as retrieval.
* **Calibrated abstention** — train/reward "I don't know" and asking clarifying questions; evaluate with metrics that penalise
  confident errors more than abstentions.
* **Verification** — self-consistency (sample several answers, check agreement), a verifier model, executing code, checking
  citations against sources.
* **Constrained decoding** for structured outputs; lower temperature for factual tasks.
* **Product design:** show sources, confidence, and make the system say what it can't do.

> **Interview angle.** Avoid "just use RAG". Say *which* failure you're fixing (missing knowledge vs ignoring context vs
> guessing incentives) and how you'd measure it: factual accuracy, citation precision, abstention rate, confident-error rate.

## D2 · Tokenisation-driven failures and numeracy

Many "dumb" LLM mistakes come from the tokeniser (week 10), not from reasoning:

* **Counting letters / spelling** ("how many r's in strawberry"): the model sees subword tokens like `straw` + `berry`, not
  characters, so it must have memorised spellings. Reversing or editing strings character by character is hard for the same reason.
* **Arithmetic:** numbers are split inconsistently (`12345` → `123` `45` in some tokenisers), so digit positions don't align
  across numbers. Fixes: **digit-by-digit** tokenisation (Llama, Qwen and DeepSeek split numbers into single digits or small
  groups), right-to-left grouping, scratch-pad reasoning, or a calculator tool.
* **Leading spaces and case:** `"Paris"` and `" Paris"` are different tokens; prompt formatting changes outputs.
* **Language cost and fairness:** some languages need 2–4× more tokens per sentence → higher latency/cost, shorter effective
  context, sometimes lower quality. Relevant for multilingual in-car assistants (Indian languages, for example).
* **Code and whitespace:** indentation tokens matter; tokenisers trained mostly on prose waste tokens on code.
* **Glitch tokens:** rare tokens whose embeddings were barely trained can produce bizarre behaviour.
* **Prompt sensitivity:** small formatting changes (chat template, trailing spaces, option order in multiple choice) can change
  answers — a real problem for evaluation reproducibility.

**On-device angle:** tokeniser choice affects vocabulary size (embedding memory), tokens per second needed for a target
words-per-second speech rate, and whether ASR transcripts (often lowercase, no punctuation) match the formats the LLM saw in
training.

> **Interview angle.** When asked about a surprising failure, first check whether the task requires character- or digit-level
> access; if so, the fix is usually a tool or representation change, not more training.

## D3 · Long context, position bias and in-context learning

* **Lost in the middle:** recall is best for information at the start (primacy, often attention-sink-related) and the end
  (recency) of a long prompt, worse in the middle. Effective context is often much shorter than the advertised window
  (week 13: RULER-style evaluation).
* **Distractors:** relevant-looking but wrong passages degrade answers more than random noise — retrieval precision matters.
* **Instruction drift:** in long chats, early instructions lose influence; systems re-inject key instructions or summaries.
* **Context management** for products: keep a short rolling summary + recent turns; retrieve older facts on demand; use **prompt /
  prefix caching** for the fixed system prompt and tool descriptions (week 14) — big TTFT savings on device too.

**In-context learning (ICL):** models learn tasks from examples in the prompt without weight updates. Mechanistic studies found
**induction heads** (attention patterns that copy what followed a previous occurrence of the current token) emerge during training
and underpin much copying/ICL; theoretical views interpret ICL as implicit Bayesian inference or as gradient-descent-like updates
inside attention. Practical consequences: example order and format matter; labels in examples matter less than format for some
tasks; more examples help up to a point, then plateau.

**Reasoning traces:** chain-of-thought improves multi-step tasks; RL-trained reasoning models (week 17) generate long traces whose
length you can budget (Qwen3's thinking budget). Traces aren't guaranteed to be faithful explanations of how the answer was produced.

> **Interview angle.** "Our assistant forgets the user's preferences after 30 turns" → explain position bias and context
> growth, then propose summarisation memory + retrieval of user facts + prefix caching, and an evaluation that tests recall at
> different turn depths.

## D4 · Tool use, function calling and agents

**How models learn tool use:** SFT on traces where the assistant emits a structured call (JSON with a function name and arguments),
receives the result as a tool message, and continues; then **RL in environments** with verifiable outcomes (did the code pass, did
the booking succeed) — Kimi K2's synthetic tool environments, MiniMax's SWE environments, GLM's agentic RL (weeks 17–19). The chat
template defines how tools are described (usually a JSON schema in the system prompt).

**Making calls reliable:**

* **Schema-constrained decoding** (grammars/JSON schema → token masks, week 14) guarantees parseable output; still validate types,
  ranges and enums in code.
* **Validation and repair loop:** on error, return a concise error message to the model and let it retry (bounded retries).
* **Few, well-named tools** with clear descriptions beat many overlapping ones; small on-device models degrade quickly with large
  tool sets — route to a subset first.

**Agent loop (ReAct-style):** think → act (tool call) → observe → repeat until done; plus planning, memory and stop conditions.
**Failure modes:** looping, wrong tool, hallucinated arguments, ignoring tool errors, long-horizon drift, cost/latency blow-up.

**Safety for actions** (critical in a car): require confirmation for consequential or irreversible actions (calls, messages,
navigation changes, payments), allow-list tools per context (no window control while driving fast?), rate limits, and treat **tool
outputs and retrieved text as untrusted** — **prompt injection** (instructions hidden in an email, web page or document) is the main
security risk of agents. Keep the system's authority separate from data.

**On-device agents:** a 1–4B model with a handful of vehicle/phone tools, constrained decoding, a router to the cloud for open-ended
tasks, and deterministic code paths for safety-relevant actions.

> **Interview angle.** For any agent design, discuss three things unprompted: how you validate tool calls, how you confirm
> consequential actions, and how you defend against prompt injection from tool outputs.

## D5 · Evaluating LLM features, and on-device RAG

**Evaluation beyond benchmarks:**

* **Task-specific eval sets** built from real (consented, anonymised) user requests + hard cases; stratify by slice (language,
  domain, length, noisy ASR input).
* **Metrics:** exact match / execution success where possible; rubric scores; pairwise preference (win rate) against the current
  model; for RAG — **retrieval recall@k**, **faithfulness** (claims supported by retrieved text), **answer relevance**, citation
  precision; latency and cost.
* **LLM-as-judge** is scalable but biased: **position bias** (prefers the first/second option — evaluate both orders and
  average), **verbosity bias**, **self-preference** (favouring outputs from its own family), sensitivity to rubric wording.
  Calibrate against human labels (agreement, Cohen's κ) before trusting it.
* **Regression suites** in CI, **contamination** checks (benchmarks leaked into training data), online A/B tests with guardrail
  metrics (complaints, task abandonment).

**On-device RAG design (e.g. owner's-manual Q&A in a car, offline):**

1. **Ingestion:** split the manual into chunks (~200–400 tokens, respecting headings/tables), keep metadata (section, page).
2. **Embedding:** a small embedding model (~20–100M params, int8) on the NPU/CPU; precompute chunk embeddings offline and ship them.
3. **Index:** a few thousand chunks fit in a flat int8 matrix (exact search is fast); add **BM25 keyword search** and fuse rankings
   (hybrid search handles part numbers and error codes that embeddings miss).
4. **Generation:** the top 3–5 chunks + question into a 1–4B LLM with instructions to answer only from sources and cite them; abstain
   if the answer isn't present.
5. **Evaluation:** recall@k on a labelled question set, faithfulness, abstention when the answer is absent, latency end to end.

> **Interview angle.** Always separate retrieval quality from generation quality in your evaluation — otherwise you can't tell
> which component to fix.

## Questions

??* d1 [llm-behaviour] | Why do LLMs hallucinate, and which mitigations address which cause?
Next-token training rewards plausible continuations, so weakly memorised facts (rare names, numbers, citations) get reconstructed
wrongly; evaluation and post-training that score abstentions like errors reward guessing; preference training can add sycophancy;
questions beyond the knowledge cut-off or about unseen private context have no grounding; sampling and long generations compound
errors; and relevant context can be ignored or wrong. Mitigations map to causes: retrieval and tools for missing knowledge, training
and metrics that reward calibrated abstention for guessing, verification (self-consistency, verifiers, executing code, checking
citations) for reasoning errors, lower temperature and constrained decoding for format/factual tasks, and better retrieval precision
plus context management for context failures.

?? d1 [llm-behaviour, evaluation] | How would you measure hallucination for a product feature?
Build an evaluation set with known answers and with questions whose answer is not available; measure accuracy, the rate of confident
wrong answers, the abstention rate on unanswerable questions, and for grounded answers the fraction of claims supported by the cited
sources (faithfulness / citation precision), using human labels or a calibrated judge. Track these per slice and over releases.

??* d2 [tokenisation, llm-behaviour] | Why do LLMs struggle to count letters or do multi-digit arithmetic?
They operate on subword tokens, not characters: a word like "strawberry" may be one or two tokens, so the model has no direct view of its
letters and must rely on memorised spellings. Numbers may be split into inconsistent chunks, so digits of the same place value don't line
up between operands. Fixes are representational or tool-based: digit-level tokenisation, writing out intermediate steps, or calling a
calculator/code tool, rather than simply more training.

?? d2 [tokenisation, multilingual] | Why can an LLM be slower and worse in some languages, and why does it matter on device?
If the tokeniser was trained mostly on English or other well-represented languages, other scripts split into many more tokens per word
(2–4× is common), so each sentence needs more decode steps (latency, energy), uses more context, and the model saw less data per token in
training, often reducing quality. On device, where tokens per second are bandwidth-limited, this directly affects response time; choose a
model/tokeniser with good coverage of the target languages and measure per-language latency.

??* d3 [long-context] | What is "lost in the middle", and how would you design around it?
Models retrieve and use information at the beginning and end of a long context more reliably than information in the middle, and
effective context is shorter than the advertised window. Design around it by putting the most important instructions and evidence at the
start or end, keeping prompts short with retrieval of only relevant chunks (high precision), summarising older conversation into compact
memory, re-injecting key instructions, and evaluating recall at different positions and context lengths.

?? d3 [icl] | What are induction heads and why do they matter for in-context learning?
They are attention heads (typically a pair of circuits across two layers) that look for a previous occurrence of the current token and copy
the token that followed it, implementing pattern completion like [A][B] … [A] → [B]. They emerge abruptly during training, coinciding with a
jump in in-context learning ability, and are believed to underlie much of LLMs' ability to copy and follow patterns from examples in the prompt.

??* d4 [tool-use, agents] | How are LLMs trained to call tools, and how do you make function calling reliable in production?
Through supervised fine-tuning on traces where the assistant emits structured calls, receives tool results and continues, then
reinforcement learning in environments with verifiable outcomes; the chat template defines tool schemas and message roles. In production:
describe a small set of well-named tools with JSON schemas, use schema-constrained decoding so calls always parse, validate arguments in
code (types, ranges, enums, permissions), feed concise errors back for a bounded retry, confirm consequential actions with the user, and log
and evaluate call accuracy on a test suite.

??* d4 [agents, security] | What is prompt injection, and how do you defend an in-car agent against it?
Malicious instructions embedded in data the model reads — a message, email, web page, calendar entry or retrieved document — that try to make
the model ignore its instructions or misuse tools ("ignore previous instructions and text this number…"). Defences: treat all tool outputs and
retrieved content as untrusted data, never as instructions; keep authority in the system and user turns; restrict tools per context with
allow-lists; require explicit user confirmation for consequential actions; validate arguments in code; limit what data can be sent out; and test
with adversarial examples. No single prompt-based defence is sufficient.

??* d5 [evaluation, llm-judge] | What are the pitfalls of using an LLM as a judge, and how do you mitigate them?
Position bias (preferring the first or second answer), verbosity bias (preferring longer answers), self-preference for outputs in its own style or
family, sensitivity to rubric wording, and inconsistency across runs. Mitigate by judging both orders and averaging or requiring agreement, using
clear rubrics with reference answers, controlling for length, using a different model family as judge, sampling multiple judgments, and validating
the judge against human labels (agreement or Cohen's κ) before using it for decisions.

??* d5 [rag, edge] | Design an offline owner's-manual Q&A feature for a car head unit.
Ingest the manual into section-aware chunks with metadata; embed them offline with a small int8 embedding model and ship the vectors; at runtime
embed the question on the NPU/CPU, search a flat int8 index plus BM25 keyword search (for part numbers and warning codes) and fuse the rankings;
pass the top 3–5 chunks to a 1–4B quantised LLM instructed to answer only from them, cite sections, and abstain when the answer isn't present.
Evaluate retrieval recall@k, answer faithfulness, abstention on unanswerable questions and end-to-end latency; update the index via OTA with new
manual versions.

?? d5 [rag] | Why use hybrid (BM25 + embedding) retrieval instead of embeddings alone?
Dense embeddings capture meaning and paraphrase but can miss exact tokens such as part numbers, error codes, product names and rare terms, and they
degrade out of domain. BM25 matches exact terms well but misses paraphrases. Combining them (e.g. reciprocal rank fusion) gives better recall across
both query types, and it's cheap to run on device.
