| Class | Examples | Typical budget | ML notes |
|---|---|---|---|

| Mobile SoC NPU | Qualcomm Hexagon NPU, Apple Neural Engine, MediaTek APU, Google Tensor TPU | 10s of TOPS (int8/int4), shared LPDDR5X ~50–100 GB/s | on-device LLMs, vision, ASR; delegate graphs via QNN / Core ML / NNAPI-successors |
| Automotive SoC | Qualcomm **SA8295 / Snapdragon Ride/Cockpit**, NVIDIA **Orin/Thor**, TI TDA4, Renesas R-Car, Mobileye | 10s–1000+ TOPS, safety islands | cockpit assistants, DMS, ADAS; QNX/Linux/Android Automotive; functional safety |
| Edge GPU | Jetson Orin Nano/AGX | 20–275 TOPS, 8–64 GB | TensorRT, CUDA, FP16/INT8 |

**Why TOPS numbers mislead:** peak TOPS assume dense int8 GEMMs with perfect utilisation. Real models are limited by **memory
bandwidth**, unsupported operators (fall back to CPU), layout conversions, small layers and synchronisation. Always benchmark the
actual model on the actual device.

**Memory types:** on-chip SRAM (fast, small — the working set), flash/ROM (weights on MCUs, often executed/read in place),
DRAM/LPDDR (mobile/automotive, shared with CPU/GPU), TCM (tightly coupled memory on DSPs). Energy per access rises ~100× from SRAM
to DRAM — moving data costs more energy than computing on it.

> the full ASR runs on the application processor or NPU only after the wake word fires."

## D2 · The roofline model

Attainable performance for a kernel with **arithmetic intensity** $I$ (FLOPs per byte of memory traffic) on hardware with peak
compute $P$ and bandwidth $B$:

```math
\text{Perf}(I)=\min(P,\ I\cdot B),\qquad I^*=\frac{P}{B}\ \text{(ridge point)}
```

Below the ridge point you're **memory-bound** (faster memory or less traffic helps; more compute doesn't); above it, **compute-bound**.

**Intensity of common layers** (int8, ignoring caches; bytes = weights + inputs + outputs):

* **Linear / GEMM** $(M\times K)(K\times N)$: $I=\frac{2MKN}{MK+KN+MN}$. Batch-1 matrix–vector ($M=1$): $I\approx2$ ops/byte → deeply
  memory-bound. That's LLM decode.
* **Standard 3×3 conv** with many channels: high reuse → often compute-bound.
* **Depthwise 3×3 conv:** ~$2\cdot9$ ops per input element loaded and little weight reuse → $I\approx$ a few → memory-bound.
* **Element-wise ops, norms, activations:** $I<1$ → always memory-bound → fuse them.
* **Attention decode:** reading the KV cache for one query: $I\approx1$–2.

**Worked example:** an NPU with 40 TOPS int8 and 60 GB/s → ridge ≈ 670 ops/byte. A 3B-parameter int4 model decoding at batch 1 reads
~1.6 GB per token at $I\approx4$ ops/byte → attainable ≈ 240 GOPS ≪ 40 TOPS; speed ≈ 60 GB/s ÷ 1.6 GB ≈ 37 tokens/s max. Prefill of 512
tokens reuses each weight 512× → compute-bound.

**Hierarchical roofline:** separate ceilings for DRAM, L2/SRAM and registers; tiling raises the effective intensity at the outer
levels. Also "ceilings" for unvectorised code or non-Tensor-Core math.

> **Interview angle.** Given peak TOPS, bandwidth and a layer shape, say in one minute whether it's compute- or memory-bound and what
> optimisation follows (quantise weights / fuse / batch / tile).

## D3 · Fixed-point arithmetic

You know this from DSP — interviews for embedded ML expect it to be crisp.

**Qm.n format:** a signed integer interpreted as $x = q\cdot2^{-n}$ with $m$ integer bits and $n$ fractional bits (plus sign). **Q15**
(int16, $n=15$): range $[-1, 1-2^{-15}]$, resolution $3.05\times10^{-5}$. **Q31** for int32.

**Multiplication:** Q15 × Q15 → Q30 in 32 bits; shift right by 15 (with **rounding**: add $2^{14}$ first) to return to Q15;
**saturate** to $[-32768, 32767]$. The one overflow case: $-1\times-1=+1$, not representable in Q15 → saturate.

**Addition:** same Q format required; can overflow → saturate or use guard bits. **Accumulators** are wider: int8 × int8 products are
int16, summed in **int32** (a 3×3×256 conv sums 2,304 products — up to ~2^29 — safe in int32). DSPs have 40/48/64-bit accumulators with
guard bits.

**Rounding modes:** truncation (floor, biased by −½ LSB), round-half-up, round-to-nearest-even, stochastic rounding (unbiased, used in
low-precision training).

**Quantisation noise:** uniform quantiser with step $\Delta$ → noise power $\Delta^2/12$ → SQNR ≈ **6.02 b + 1.76 dB** for a full-scale
sine; every extra bit buys ~6 dB.

**Block floating point:** a block of mantissas shares one exponent — used in FFTs on DSPs, and conceptually identical to MX/micro-scaled
formats in modern AI accelerators (week 22).

**Neural-net mapping:** int8 inference is fixed-point arithmetic with per-tensor/per-channel scales; requantisation multiplies by a
fixed-point multiplier and shifts (week 21). Non-linearities (sigmoid, tanh, exp, softmax) use lookup tables or polynomial
approximations in fixed point.

> **Interview angle.** "Multiply two Q15 numbers in C" — `int32_t p = (int32_t)a * b; p = (p + (1 << 14)) >> 15; return sat16(p);` — and
> mention the −1 × −1 corner case.

## D4 · Memory planning and data movement on device

**Peak memory ≠ model size.** On an MCU you need: weights (flash) + the **tensor arena** in SRAM for activations + runtime overhead.
Peak activation memory is set by the largest set of tensors alive at the same time.

**Memory planning:** compute each tensor's lifetime (from producing op to last consumer) in the execution order, then assign offsets
in a single arena so tensors with overlapping lifetimes don't overlap in memory — a 2-D bin-packing problem solved greedily (sort by
size, place at the lowest non-conflicting offset). TFLite Micro and ExecuTorch do this ahead of time. **In-place ops** (ReLU, add into
an input buffer) save more. Operator order matters: different topological orders of a branching graph have different peaks.

**Patch-based inference (MCUNetV2):** the first CNN stages have huge activations; process them in spatial patches to cut peak SRAM by
4–8×, at some recomputation cost.

**Data movement:** DMA engines copy the next tile/weights while the core computes the current one (**double buffering**); keep hot
weights in TCM/SRAM; align buffers for SIMD; prefer NHWC (channels last) for most embedded kernels.

**Measuring:** cycle counters (DWT on Cortex-M), per-layer timing, peak RAM via arena high-water mark, energy with a power analyser
(µJ per inference), latency distributions (worst case matters for real time), thermal throttling on phones/automotive over long runs.

> **Interview angle.** "Your model fits in flash but crashes at runtime on the MCU" → the arena is too small (peak activations), stack
> overflow, or alignment; print the planner's arena usage, reduce the largest intermediate (patch-based, smaller input, earlier
> downsampling).

## D5 · Real-time inference pipelines for audio

Real-time audio has hard deadlines: every hop (e.g. 10 ms or 1–4 ms for hearing aids) the next output buffer must be ready.

**Audio callback rules:** no memory allocation, no locks that can block, no file/network I/O, no unbounded loops, no logging — anything
with non-deterministic timing can cause a **buffer underrun** (output not ready → glitch/click) or **overrun** (input not consumed →
samples dropped).

**Decoupling inference from the callback:** the callback writes input frames into a **lock-free single-producer single-consumer (SPSC)
ring buffer** and reads processed frames from another; a worker thread (or another core / DSP) runs the model. The ring buffer uses
atomic head/tail indices with acquire/release ordering, power-of-two sizes for cheap wraparound, and tracks overruns/underruns. Size it
for worst-case inference jitter while keeping latency budget.

**Latency budget accounting** (example in-car NS at 16 kHz): ADC/driver buffering 2–4 ms + analysis window 20 ms (algorithmic) +
lookahead 0 + compute ≤ 5 ms (must be < hop with margin) + output buffering 2–4 ms + DAC.

**Scheduling:** pin the audio thread to a core with real-time priority; avoid priority inversion; batch non-real-time work (e.g. ASR)
elsewhere; on DSPs use the RTOS task model; measure **worst-case execution time (WCET)**, not averages; keep a fallback path (bypass or
classic DSP) if the model misses its deadline.

**Model-side choices:** causal, frame-synchronous models with explicit state; fixed-shape inputs; avoid ops with data-dependent runtime;
quantised kernels with predictable timing.

> **Interview angle.** You asked to cover underruns/overruns — be ready to draw the callback → ring buffer → inference thread → ring
> buffer → callback diagram and explain how you'd size the buffers and what happens when inference is late.

## Questions

??* d1 [edge-hardware] | Why can a model run slower on a 40-TOPS NPU than its FLOPs suggest?
Peak TOPS assume dense, well-shaped int8 matmuls with perfect data reuse. Real models hit memory-bandwidth limits (low arithmetic intensity
layers like depthwise convs, element-wise ops, decode-time matrix–vector products), have operators the NPU doesn't support (falling back to
CPU with costly data transfers), need layout or precision conversions, have many small layers with launch/synchronisation overhead, and may
throttle thermally. Profiling per layer on the device is the only reliable measure.

??* d2 [roofline] | Explain the roofline model and use it to classify LLM decode at batch 1.
Attainable performance = min(peak compute, arithmetic intensity × memory bandwidth); the ridge point P/B separates memory-bound from
compute-bound kernels. LLM decode at batch 1 is a series of matrix–vector products: each weight byte is used for ~1–2 operations (int8:
2 ops per byte; int4: ~4), far below typical ridge points of hundreds of ops/byte, so it's memory-bound: tokens/s ≈ bandwidth ÷ bytes read per
token. Optimisations that cut bytes (quantisation, MoE, KV compression) or increase work per byte (batching, speculative decoding) help;
more TOPS doesn't.

?? d2 [roofline] | Compute the arithmetic intensity of a 1024×1024 int8 matrix–vector product and a 512×1024×1024 matmul.
Matrix–vector: 2·1024·1024 ≈ 2.1M ops; bytes ≈ 1 MB weights + small vectors → ≈2 ops/byte (memory-bound everywhere). Matmul with M = 512:
2·512·1024·1024 ≈ 1.07G ops; bytes ≈ 512K (input) + 1M (weights) + 512K (output, int8) ≈ 2 MB → ≈512 ops/byte, near or above the ridge point of
most NPUs, so compute-bound. Batching/sequence length is what moves you along the roofline.

??* d3 [fixed-point] | How do you multiply two Q15 numbers correctly?
Multiply as int16 × int16 into an int32 product, which is in Q30. Add the rounding constant 2^14, arithmetic-shift right by 15 to get back to
Q15, and saturate to [−32768, 32767]. The only overflow case is (−1)·(−1) = +1, which isn't representable in Q15 and must saturate to 32767.
DSP instructions often do this in one cycle (fractional multiply with saturation).

?? d3 [fixed-point] | What SQNR does an 8-bit uniform quantiser give, and what does that imply for int8 neural networks?
SQNR ≈ 6.02·b + 1.76 dB for a full-scale sine, ≈ 50 dB at 8 bits; for Gaussian-like data clipped at a few σ it's lower (~35–40 dB). Each bit adds ~6
dB. For networks this means int8 is usually sufficient for weights and activations if the range is well chosen (per-channel scales, good
calibration), but outliers that force a large scale waste most of the levels, which is why outlier handling matters more than bit count at 8 bits.

??* d4 [memory] | How does a runtime like TFLite Micro decide how much SRAM a model needs?
It plans a single tensor arena ahead of time: from the execution order it computes each intermediate tensor's lifetime (from creation to last use),
then assigns offsets so tensors whose lifetimes overlap don't share memory — greedily placing the largest tensors first at the lowest
non-conflicting offset. The arena size is the peak of simultaneously live tensors (plus scratch buffers and alignment), not the sum. Weights stay
in flash. Reordering operators, in-place operations and patch-based execution can reduce the peak.

?? d4 [memory] | What is patch-based inference in MCUNetV2 and why does it help?
In CNNs the first layers have the largest activations (high resolution), dominating peak SRAM. Patch-based inference runs the initial stages on
small spatial patches one at a time (with overlapping halos for the receptive field), producing the downsampled feature map without ever holding
the full high-resolution activations, cutting peak memory by several times at the cost of some recomputation in the overlaps.

??* d5 [real-time, audio] | What causes buffer underruns and overruns in a real-time audio + ML system, and how do you prevent them?
An underrun happens when the output buffer isn't filled before the audio hardware needs it (processing too slow or blocked), producing clicks or
silence; an overrun when input arrives faster than it's consumed, dropping samples. Causes: inference time spikes, memory allocation or locks in
the callback, OS scheduling, I/O, logging, thermal throttling. Prevention: keep the callback minimal and real-time-safe, run inference in a separate
high-priority thread connected by lock-free SPSC ring buffers sized for worst-case jitter, measure WCET, use fixed-size pre-allocated memory, pin
threads/cores, and have a fallback (bypass or classic DSP) when deadlines are missed.

?? d5 [real-time] | How does a lock-free single-producer single-consumer ring buffer work?
A fixed-size array (power of two for cheap masking) with a write index owned by the producer and a read index owned by the consumer, both atomic.
The producer writes data then publishes the new write index with release ordering; the consumer reads the write index with acquire ordering, so
it sees the data, then consumes and publishes its read index. Full when write − read = capacity, empty when equal. No locks, so the audio thread
never blocks; counters record overruns/underruns.
