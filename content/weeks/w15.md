## D1 · GPU architecture and the CUDA programming model

**Hardware.** A GPU has many **streaming multiprocessors (SMs)** (H100 SXM: 132). Each SM runs **warps** of 32 threads in
lock-step (SIMT), has registers, a configurable **shared memory / L1** (~228 KB on H100) and **Tensor Cores** for matrix
multiply-accumulate. All SMs share an L2 cache (50 MB) and **HBM** (80 GB, ~3.35 TB/s). Rough H100 peaks: ~989 TFLOP/s dense
BF16, ~1,979 FP8; NVLink 900 GB/s per GPU (the export-limited **H800** cut NVLink to ~400 GB/s — the constraint DeepSeek
designed around).

**Memory hierarchy (latency/bandwidth):** registers ≫ shared memory ≫ L2 ≫ HBM ≫ host (PCIe ~64 GB/s) ≫ network. Every fast
kernel is about keeping data in the top levels and reusing it.

**CUDA model:** a kernel is launched over a **grid** of **thread blocks**; each block runs on one SM and its threads can share
memory and synchronise (`__syncthreads`). Index with `blockIdx`, `blockDim`, `threadIdx`.

**Performance rules of thumb:**

* **Coalescing:** consecutive threads in a warp should access consecutive addresses, so a warp's loads combine into few
  memory transactions. Strided/transposed access kills bandwidth.
* **Tiling / reuse:** for matmul $C=AB$, each block loads a tile of A and B into shared memory once and reuses each element
  many times — arithmetic intensity grows with tile size.
* **Occupancy:** enough resident warps per SM to hide memory latency; limited by registers and shared memory per block.
* **Divergence:** threads in a warp taking different branches serialise.
* **Bank conflicts** in shared memory; pad tiles to avoid them.
* **Launch overhead** (~5 µs): many tiny kernels are slow → fusion, CUDA graphs.

**Tensor Cores** need specific shapes/dtypes (multiples of 8/16, BF16/FP8/INT8); padding vocab or hidden sizes to multiples of
64/128 can noticeably speed things up.

> **Interview angle.** "Why is a naive matrix transpose slow on a GPU?" — either reads or writes are uncoalesced; fix by
> staging a tile through shared memory (with padding to avoid bank conflicts).

## D2 · Writing kernels: Triton, fusion and when to bother

**Triton** (OpenAI) lets you write GPU kernels in Python at the **block** level: each program instance handles a tile; you use
`tl.load`/`tl.store` with **masks** for boundaries, `tl.dot` for Tensor-Core matmuls, and the compiler handles thread-level
details, coalescing and shared memory. `torch.compile`'s Inductor emits Triton.

```python
@triton.jit
def softmax_kernel(out_ptr, in_ptr, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    offs = tl.arange(0, BLOCK)
    x = tl.load(in_ptr + row * n_cols + offs, mask=offs < n_cols, other=-float("inf"))
    x = x - tl.max(x, axis=0)
    num = tl.exp(x)
    tl.store(out_ptr + row * n_cols + offs, num / tl.sum(num, axis=0), mask=offs < n_cols)
```

One read and one write per element, instead of separate kernels for max, subtract, exp, sum and divide (5 reads/writes).
**Fusion** pays whenever a sequence of memory-bound ops can share one pass over memory.

**Other tools:** CUDA C++ with CUTLASS/CuTe for peak GEMM performance; **TileLang** (a tile-level DSL — DeepSeek-V4 used it
for kernel development); ThunderKittens; and for edge, vendor kernel libraries (CMSIS-NN, XNNPACK, Hexagon NN) and compilers
(TVM, IREE).

**When to write a custom kernel:** profiling shows a memory-bound hotspot (norm + activation chains, attention variants,
quantised GEMMs, MoE dispatch, sampling) that `torch.compile` can't fuse, or you need a new algorithm (FlashAttention-style
tiling for a new attention type, a custom sparse pattern). Otherwise rely on compilers and libraries.

**Profiling:** Nsight Systems (timeline: gaps, sync points, overlap) and Nsight Compute (per-kernel: achieved bandwidth/FLOPs,
occupancy, stall reasons), `torch.profiler` for the PyTorch view.

> **Interview angle.** "How would you speed up RMSNorm?" — it's memory-bound: fuse it with the following matmul's input
> load or with the residual add, use one pass with a block-level reduction, vectorised loads, and FP32 accumulation.

## D3 · Collectives and data parallelism

**Collectives** (NCCL on GPUs, Gloo on CPU) — know what each does and its cost for a message of $S$ bytes on $N$ ranks with
per-link bandwidth $B$:

| Collective | Result | Ring cost (time) |
|---|---|---|
| broadcast | everyone gets rank 0's data | ≈ $S/B$ |
| reduce-scatter | each rank gets 1/N of the sum | $\frac{N-1}{N}\frac{S}{B}$ |
| all-gather | everyone gets all shards | $\frac{N-1}{N}\frac{S}{B}$ |
| **all-reduce** | everyone gets the full sum | $2\frac{N-1}{N}\frac{S}{B}$ (= reduce-scatter + all-gather) |
| all-to-all | rank i sends chunk j to rank j | $\frac{N-1}{N}\frac{S}{B}$, latency-heavy |

The ring all-reduce's bandwidth term is (almost) independent of $N$ — why data parallelism scales. Trees reduce latency for
small messages; NCCL picks algorithms automatically.

**Data parallelism (DDP):** every rank holds a full model replica and a different data shard; after backward, gradients are
**all-reduced** (averaged) so all replicas take the same step. PyTorch DDP buckets gradients (~25 MB) and launches all-reduce
for a bucket as soon as its gradients are ready, **overlapping communication with the rest of backward**. Requirements:
identical init (broadcast at start), `DistributedSampler` (different data per rank, `set_epoch` each epoch), and care with
BatchNorm (SyncBatchNorm) and with unused parameters.

**Launching:** `torchrun --nproc_per_node=8 train.py` sets `RANK`, `LOCAL_RANK`, `WORLD_SIZE`, `MASTER_ADDR`; in code
`dist.init_process_group("nccl")`, `torch.cuda.set_device(local_rank)`, wrap with `DDP(model, device_ids=[local_rank])`.

**Gradient accumulation with DDP:** use `model.no_sync()` on the non-final micro-steps to avoid all-reducing every
micro-batch.

> **Interview angle.** "DDP training hangs at the first step" — a collective mismatch: one rank skipped a backward (unused
> parameters / data-dependent branch), different numbers of batches per rank, or a rank crashed. Use `find_unused_parameters`,
> `drop_last`, and `TORCH_DISTRIBUTED_DEBUG=DETAIL`.

## D4 · Sharding and model parallelism: ZeRO/FSDP, TP, PP, SP/CP, EP

When the model doesn't fit on one GPU (recall ~16 bytes/param for mixed-precision Adam):

* **ZeRO** (DeepSpeed) shards across data-parallel ranks: stage 1 the **optimiser state**, stage 2 + **gradients**, stage 3 +
  **parameters**. **FSDP/FSDP2** (PyTorch) is ZeRO-3: before each layer's forward, **all-gather** its parameters; free them
  after; in backward, all-gather again, compute gradients, **reduce-scatter** them so each rank keeps only its shard. Memory per
  GPU ≈ 16N/world_size + activations; communication ≈ 1.5× DDP. Prefetching overlaps the gathers with compute.
* **Tensor parallelism (Megatron-LM):** split individual matmuls. In the MLP, split $W_1$ by **columns** (each GPU computes a
  slice of the hidden units, apply GeLU locally) and $W_2$ by **rows** (partial sums), then **one all-reduce** per MLP; attention
  splits by heads similarly. Needs very fast interconnect (within a node, NVLink). **Sequence parallelism** additionally shards
  the LayerNorm/dropout activations along the sequence between TP regions (all-reduce becomes reduce-scatter + all-gather).
* **Pipeline parallelism:** split layers into stages on different GPUs; feed **micro-batches** to keep stages busy. GPipe has a
  **bubble** fraction ≈ $(p-1)/(m+p-1)$ for $p$ stages and $m$ micro-batches; **1F1B** interleaves forward and backward to cap
  activation memory; interleaved/virtual stages shrink the bubble; zero-bubble schedules split backward into input-grad and
  weight-grad parts. **DualPipe** (DeepSeek-V3) feeds micro-batches from both ends of the pipeline and overlaps each chunk's
  computation with the MoE all-to-all and PP communication of another, almost eliminating bubbles and hiding EP communication.
* **Context parallelism:** for very long sequences, shard the sequence across GPUs; **ring attention** passes K/V blocks around a
  ring while each GPU computes attention for its queries (online softmax again).
* **Expert parallelism:** experts on different GPUs with all-to-all dispatch/combine (week 12).

**Combining them ("4D/5D parallelism"):** TP within a node (fast NVLink), PP across nodes, DP/FSDP over everything, CP for long
context, EP for MoE. DeepSeek-V3 used 16-way PP (DualPipe), 64-way EP across 8 nodes, ZeRO-1 DP, and **no tensor
parallelism** — avoiding TP was a deliberate choice for the H800's limited NVLink.

> **Interview angle.** Be able to draw column-then-row parallel MLP and say why only one all-reduce is needed: the GeLU is
> element-wise on the column shards, and the row-parallel matmul produces partial sums that are reduced once.

## D5 · Efficiency at scale: memory tricks, MFU and the DeepSeek case study

**Activation memory** often dominates: ~$sbh(34+5as/h)$ bytes per layer for a transformer (Korthikanti et al.), growing with
sequence length. Tools: **activation checkpointing** (store only layer inputs, recompute in backward: ~33% more compute;
*selective* checkpointing recomputes only cheap, memory-heavy ops such as attention softmax), CPU offload of activations or
optimiser state, sequence/context parallelism, and FlashAttention (no $T^2$ activations).

**MFU (model FLOPs utilisation)** = achieved model FLOPs ($6N$ per token × tokens/s) ÷ peak hardware FLOPs. Good large-scale
training reaches ~35–55% (BF16). Losses come from communication not overlapped, pipeline bubbles, memory-bound ops, data
loading, and stragglers.

**Reliability:** at thousands of GPUs, failures happen daily — asynchronous/distributed checkpointing, fast restart, detecting
silent data corruption and stragglers, deterministic data ordering for resume.

**Case study — how DeepSeek trained V3 cheaply** (2.788M H800 GPU-hours for 671B-A37B on 14.8T tokens):

1. **Architecture for efficiency:** MoE with 37B active of 671B; MLA for a small KV cache; MTP for denser signal.
2. **FP8 mixed-precision training** with fine-grained tile/block scaling and FP32 promotion of accumulations — first validated
   at this scale.
3. **DualPipe** to overlap computation with communication; custom all-to-all kernels using few SMs (warp specialisation) so most
   SMs keep computing; node-limited routing to bound cross-node traffic.
4. **Memory savings:** recompute RMSNorm and MLA up-projections in backward, keep EMA of weights on CPU, share embedding/head
   with the MTP module across pipeline stages → no tensor parallelism needed.
5. **Hardware co-design:** decisions shaped around H800 limits (reduced NVLink), later summarised in their ISCA 2025 paper on
   hardware lessons. V4 adds Muon, FP4 QAT for experts, TileLang kernels, deterministic/batch-invariant kernels for RL, and
   fine-grained EP overlap.

> **Interview angle.** "How did Chinese labs get frontier results with less compute?" — co-design: sparse architectures (MoE,
> MLA/sparse attention), low precision (FP8 → FP4), communication-aware parallelism (DualPipe, DeepEP, node-limited routing),
> custom kernels, and efficient RL (GRPO without a critic). Export controls on GPUs made efficiency a necessity.

## Questions

??* d1 [gpu] | Explain the GPU memory hierarchy and why it determines kernel performance.
Registers (per thread) and shared memory/L1 (per SM, ~hundreds of KB) are fast but tiny; L2 (tens of MB) is shared; HBM is large
(80 GB+) but ~10–100× slower in latency and limited to a few TB/s; host memory over PCIe is slower still. Most deep-learning ops
are memory-bound, so performance depends on how many bytes move between HBM and the SMs: kernels that tile data into shared
memory, reuse it, coalesce accesses and fuse operations run near peak; those that repeatedly round-trip through HBM don't.

?? d1 [gpu] | What is memory coalescing?
When the 32 threads of a warp access contiguous, aligned addresses, the hardware combines them into a few wide memory
transactions; scattered or strided accesses need many transactions and waste bandwidth. Data layouts and indexing are chosen so
the fastest-varying thread index maps to contiguous memory (e.g. row-major access along rows).

??* d2 [kernels] | Why does kernel fusion speed things up? Give an example.
Element-wise and reduction ops are memory-bound: their runtime is the time to read inputs and write outputs to HBM. Running a
chain as separate kernels reads and writes intermediates each time. A fused kernel loads inputs once, does all the math in
registers/shared memory, and writes once — e.g. softmax as one kernel (max, subtract, exp, sum, divide) or RMSNorm fused with the
residual add, which cuts memory traffic several-fold. It also removes kernel-launch overhead.

?? d2 [kernels] | What is Triton and how does it differ from CUDA C++?
Triton is a Python-embedded language and compiler for GPU kernels where you program at the level of blocks/tiles rather than
individual threads: you load and store tensors of offsets with masks and use block-level ops like tl.dot and reductions; the
compiler handles thread mapping, coalescing, shared memory and Tensor Core use. It's much faster to write than CUDA C++ and
reaches near-hand-tuned performance for many kernels; CUDA/CUTLASS still win for the most demanding cases. torch.compile
generates Triton.

??* d3 [distributed] | How does ring all-reduce work and what does it cost?
Split each rank's buffer into N chunks. Reduce-scatter: in N−1 steps, each rank sends one chunk to its neighbour and adds the
chunk it receives, so at the end each rank holds the full sum of one chunk. All-gather: in N−1 more steps the reduced chunks are
passed around until every rank has all of them. Each rank sends 2(N−1)/N × S bytes in total, so bandwidth cost is nearly
independent of N; latency grows with 2(N−1) steps, so trees or hierarchical schemes are used for small messages and many nodes.

??* d3 [distributed] | How does PyTorch DDP overlap communication with computation?
Gradients are grouped into buckets (≈25 MB) in reverse order of the forward pass. Autograd hooks fire as each parameter's gradient
is ready; when a bucket is full, DDP launches an asynchronous all-reduce for it while backward continues computing earlier layers'
gradients. By the end of backward most communication is done. Use no_sync() during gradient accumulation to skip all-reduce on
intermediate micro-steps.

??* d4 [distributed] | Compare ZeRO stages and FSDP.
ZeRO shards training state across data-parallel ranks. Stage 1 shards optimiser states (the largest part with Adam), stage 2 also
shards gradients (reduce-scatter instead of all-reduce), stage 3 also shards parameters, all-gathering each layer's weights just
before use and freeing them afterwards. FSDP is PyTorch's ZeRO-3: per-GPU memory ≈ (16 bytes × N)/world size + activations, with
≈1.5× the communication of DDP, overlapped by prefetching. Use DDP when the model fits, ZeRO-1/2 when optimiser state is the
problem, FSDP/ZeRO-3 for models that don't fit.

??* d4 [distributed] | Explain Megatron-style tensor parallelism for an MLP.
For Y = GeLU(XA)B with A split by columns across GPUs ([A₁, A₂]) each GPU computes GeLU(XAᵢ) for its slice of hidden units — no
communication because GeLU is element-wise. B is split by rows so each GPU computes a partial product GeLU(XAᵢ)Bᵢ; summing them
needs one all-reduce. Attention is split by heads the same way. Each layer needs all-reduces in forward and backward, so TP is
kept within a node with fast NVLink.

?? d4 [distributed] | What is the pipeline bubble and how do schedules reduce it?
With p stages, the first stage waits idle while the last stages are still filling, and vice versa at the end: the idle fraction
is ≈ (p−1)/(m+p−1) for m micro-batches (GPipe). More micro-batches shrink it but cost activation memory. 1F1B alternates one
forward and one backward per stage to cap in-flight activations; interleaved schedules assign multiple non-adjacent layer chunks
per GPU to shrink bubbles; zero-bubble schedules split backward into input- and weight-gradient parts; DeepSeek's DualPipe feeds
micro-batches from both ends and overlaps compute with communication.

??* d5 [distributed, chinese-models] | How did DeepSeek train V3 so cheaply? List the main techniques.
Sparse architecture (MoE: 37B active of 671B; MLA; MTP), FP8 mixed-precision training with fine-grained scaling and FP32
accumulation promotion, the DualPipe pipeline schedule overlapping computation with all-to-all and PP communication, custom
dispatch/combine kernels using few SMs, node-limited routing to bound cross-node traffic, memory savings (recomputation, CPU EMA,
shared embeddings) that avoided tensor parallelism, and careful hardware co-design for H800s with reduced NVLink. Reported cost
was 2.788M H800 GPU-hours (≈$5.6M at $2/hour) for the final training, excluding research and ablations.

?? d5 [distributed] | What is MFU and what typically prevents high MFU?
Model FLOPs utilisation = (6·N·tokens per second) ÷ (number of GPUs × peak FLOP/s). It measures how much of the hardware does
useful model math. It's reduced by communication not hidden behind computation, pipeline bubbles, memory-bound operations (norms,
element-wise ops, attention at small head dims), recomputation from activation checkpointing (not counted as model FLOPs), data
loading stalls, stragglers and failures. Typical large-scale BF16 training reaches 35–55%.

?? d5 [memory] | What is activation checkpointing and what does it cost?
Instead of storing every intermediate activation for backward, store only some (e.g. each block's input) and recompute the rest
during backward. Memory for activations drops from O(L) per-layer intermediates to roughly one layer's worth plus the checkpoints,
at the cost of about one extra forward pass (~33% more compute). Selective checkpointing recomputes only cheap-to-recompute,
memory-heavy parts (e.g. attention scores, norms) to get most of the memory savings with little extra compute.
