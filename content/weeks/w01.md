## D1 · The Python data model and complexity

Coding rounds for ML roles are usually "implement X in Python/NumPy/PyTorch", not hard LeetCode, but you are
judged on whether your Python is idiomatic and whether you know what each operation **costs**.

**Built-in containers and their costs**

| Operation | list | dict / set | deque |
|---|---|---|---|
| index / lookup | O(1) by index | O(1) average by key | O(n) by index |
| append / add | O(1) amortised | O(1) average | O(1) both ends |
| insert/pop at front | **O(n)** | – | O(1) |
| `x in c` | **O(n)** | O(1) average | O(n) |

Dicts and sets are hash tables: keys must be **hashable** (immutable: `int`, `str`, `tuple` of hashables).
A `list` can't be a dict key; convert to `tuple`. Since Python 3.7, dicts keep **insertion order**.

**Names, objects, mutability.** Variables are names bound to objects. `a = b` copies the reference, not the
object. `is` compares identity, `==` compares value. Mutable default arguments are evaluated **once**:

```python
def add(x, acc=[]):      # bug: acc is shared between calls
    acc.append(x); return acc

def add(x, acc=None):    # fix
    acc = [] if acc is None else acc
    acc.append(x); return acc
```

`copy.copy` is shallow (new outer container, same inner objects); `copy.deepcopy` recurses. In PyTorch the
analogue is `t.view(...)` (shares storage) vs `t.clone()` (new storage) — interviewers love that parallel.

**Comprehensions vs generators.** `[f(x) for x in xs]` builds the whole list; `(f(x) for x in xs)` yields lazily
in O(1) memory. `sum(x*x for x in xs)` never materialises the list.

**Useful standard library for interviews:** `collections.Counter`, `defaultdict`, `deque`, `heapq`
(min-heap: `heappush`, `heappop`, `nlargest`), `bisect` (binary search in a sorted list), `itertools`
(`accumulate`, `groupby`, `islice`, `product`, `combinations`), `functools` (`lru_cache`, `partial`,
`reduce`).

> **Interview angle.** When you write a loop, say its complexity out loud. When you reach for `list.pop(0)`
> or `x in some_list` inside a loop, switch to `deque` or `set` and say why.

## D2 · Iterators, generators, closures and decorators

**Iterator protocol.** An iterable has `__iter__()` returning an iterator; an iterator has `__next__()` that
raises `StopIteration` when exhausted. A `for` loop is just that protocol. A PyTorch `DataLoader` is an
iterable; each `iter(loader)` creates a fresh iterator (and, with workers, fresh worker processes).

**Generators** are functions with `yield`. They keep their local state between calls, so they are the natural
way to write streaming pipelines:

```python
def read_frames(stream, hop):
    buf = []
    for sample in stream:
        buf.append(sample)
        if len(buf) == hop:
            yield buf; buf = []
```

`yield from sub()` delegates to another generator. Generators are single-pass: once consumed they are empty.

**Closures** capture variables from the enclosing scope *by reference*, which produces the classic
late-binding bug:

```python
fs = [lambda: i for i in range(3)]   # all return 2
fs = [lambda i=i: i for i in range(3)]  # 0, 1, 2
```

**Decorators** are functions that take a function and return a new one. Always use `functools.wraps` so the
wrapped function keeps its name and docstring.

```python
import functools, time
def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        t = time.perf_counter(); out = fn(*args, **kwargs)
        print(f"{fn.__name__}: {time.perf_counter() - t:.3f}s"); return out
    return wrapper
```

A decorator **with arguments** is a function returning a decorator (three levels of nesting).
`@functools.lru_cache(maxsize=None)` memoises pure functions with hashable arguments.

> **Interview angle.** `torch.no_grad()` works both as a context manager and as a decorator; `@torch.compile`
> is a decorator that returns an optimised callable. Being able to explain how that's possible (classes with
> `__call__`, `__enter__`/`__exit__`) shows you understand the language, not just the library.

## D3 · Classes, dunder methods, context managers and concurrency

**Dunder methods** let your objects plug into Python syntax: `__len__`, `__getitem__` (makes a class usable as a
map-style `Dataset`), `__iter__`, `__call__` (`nn.Module.__call__` runs hooks then `forward`), `__repr__`,
`__eq__`/`__hash__` (define both or neither), `__enter__`/`__exit__`.

**dataclasses** remove boilerplate for config objects: `@dataclass(frozen=True)` makes them immutable and
hashable — good for experiment configs. `__slots__` saves memory for millions of small objects.

**Context managers** guarantee cleanup:

```python
from contextlib import contextmanager
@contextmanager
def eval_mode(model):
    was = model.training
    model.eval()
    try:
        yield model
    finally:
        model.train(was)
```

**Concurrency in one paragraph.** CPython has a Global Interpreter Lock: only one thread runs Python
bytecode at a time. Threads help for **I/O-bound** work (downloads, disk); **CPU-bound** Python needs
`multiprocessing` (separate processes, data pickled between them). NumPy and PyTorch release the GIL inside
their C/CUDA kernels, so threads can still help there. That's why `DataLoader(num_workers=k)` uses processes:
decoding and augmentation are Python-heavy. (Free-threaded CPython builds without a GIL exist since 3.13 but
most of the ecosystem still assumes the GIL.)

**Exceptions:** catch the narrowest exception you can, never a bare `except:`; use `raise ... from err` to keep
the chain.

> **Interview angle.** "Implement an LRU cache" tests hashing + a doubly linked list (or `OrderedDict`). It's the
> same structure as a KV-cache eviction policy or an on-device model cache.

## D4 · Algorithm patterns that show up in ML coding rounds

You rarely need dynamic programming wizardry, but these patterns appear constantly:

* **Top-k with a heap.** Keep a min-heap of size k: O(n log k). `heapq.nlargest(k, xs)` does it for you. This is
  top-k sampling, beam search and k-nearest-neighbours.
* **Sliding window / two pointers.** Moving averages, longest sub-array under a constraint, framing audio.
* **Binary search on a sorted array or on the answer.** `bisect` for quantile lookups and for finding a
  threshold that meets a recall target.
* **Hash-map counting.** `Counter` for n-grams, BPE pair counts, confusion matrices.
* **Intervals.** Merge overlapping segments: VAD segments, diarisation turns.
* **Streaming statistics.** You can't hold the stream in memory.

Welford's online mean/variance is numerically stable (the naive $E[x^2]-E[x]^2$ cancels catastrophically):

```math
\mu_n = \mu_{n-1} + \frac{x_n-\mu_{n-1}}{n},\qquad M_n = M_{n-1} + (x_n-\mu_{n-1})(x_n-\mu_n),\qquad \sigma^2_n = \frac{M_n}{n-1}
```

**Reservoir sampling** picks a uniform random sample of size k from a stream of unknown length: keep the first
k items, then replace a random slot with item $i$ with probability $k/i$.

> **Interview angle.** Always state input sizes and complexity, write a tiny test case first, and handle the
> edge cases (empty input, k > n, ties) explicitly. Interviewers grade the process as much as the answer.

## D5 · The ML mindset: generalisation, leakage and baselines

Before any algorithm question, interviewers check that you think like an ML engineer.

**The goal is generalisation.** We minimise empirical risk on training data as a proxy for expected risk on
unseen data. The gap between them is what regularisation, more data and validation discipline control.

**Bias–variance decomposition** (squared loss, $y = f(x) + \varepsilon$):

```math
\mathbb{E}\big[(y-\hat f(x))^2\big] = \underbrace{\big(f(x)-\mathbb{E}\hat f(x)\big)^2}_{\text{bias}^2} + \underbrace{\mathrm{Var}\,\hat f(x)}_{\text{variance}} + \underbrace{\sigma^2}_{\text{noise}}
```

Simple models: high bias. Flexible models: high variance. Large neural nets complicate the picture (**double
descent**: test error can fall again past the interpolation threshold), but the decomposition is still the
right first answer.

**Splits.** Train to fit, validation to choose hyper-parameters and early-stop, test **once** at the end. Use
k-fold CV for small data. Split by the unit that must generalise: by **speaker** for speech, by **car/session**
for in-cabin audio, by **time** for forecasting (never shuffle the future into training).

**Leakage** is the most common real-world failure: normalisation statistics computed on the whole dataset,
duplicates across splits, features that encode the label (e.g. a "processed_by_specialist" flag), the same
recording augmented into both train and test.

**Baselines first.** Majority class, linear model, a classic DSP pipeline (spectral subtraction / Wiener
filter for enhancement). If you can't beat the baseline, the bug is probably in the data or the evaluation.

**Error analysis** beats architecture tweaking: slice metrics by condition (SNR, speaker, noise type, device),
look at the worst examples, then decide whether you need more data, better labels or a better model.

> **Interview angle.** For any "how would you build X" question, say: metric → data and splits → baseline →
> model → error analysis → deployment constraints. You'll reuse this skeleton for system design in week 26.

## Questions

??* d1 [python] | What is the time complexity of `x in my_list` vs `x in my_set`, and why?
List membership is O(n): Python scans element by element. Set membership is O(1) on average because a set is a
hash table: it hashes `x`, jumps to a bucket, and compares only the few entries there (worst case O(n) with
pathological collisions). So inside a loop, convert the list to a set once (O(n)) and the whole loop drops
from O(n·m) to O(n+m). Elements must be hashable.

?? d1 [python] | Explain the mutable default argument bug and how to fix it.
Default values are evaluated once, when the `def` statement runs, and stored on the function object. A
mutable default such as `acc=[]` is therefore shared by every call that doesn't pass `acc`, so state leaks
between calls. Fix: use `acc=None` and create a fresh list inside the function
(`acc = [] if acc is None else acc`).

?? d1 [python, pytorch] | What's the difference between a shallow copy and a deep copy? What's the PyTorch analogue?
A shallow copy creates a new outer container whose elements are the same objects; mutating an inner object is
visible through both. A deep copy recursively copies everything. In PyTorch, `view`, slicing, `transpose` and
`expand` return tensors that **share storage** with the original (changing one changes the other), while
`clone()` allocates new storage. `detach()` shares storage but cuts the autograd graph;
`detach().clone()` gives an independent copy without history.

??* d2 [python] | What is a generator, and why would you use one in a data pipeline?
A generator is a function containing `yield`; calling it returns an iterator that runs the body lazily, pausing
at each `yield` and keeping its local state. Pipelines use them to stream data (read → decode → frame → batch)
in constant memory, start producing output before the input is finished, and compose stages cleanly. They are
single-pass, and their work happens in the consuming thread, so CPU-heavy stages may still need worker
processes.

?? d2 [python] | Why does `[lambda: i for i in range(3)]` return 2 for every function?
Closures capture the variable `i`, not its value at definition time. By the time the lambdas are called the
loop has finished and `i` is 2. Fix by binding the value as a default argument (`lambda i=i: i`) or with
`functools.partial`.

?? d2 [python] | How do you write a decorator that takes arguments, e.g. `@retry(times=3)`?
Three levels: `retry(times)` returns a decorator; the decorator takes `fn` and returns `wrapper`; `wrapper`
calls `fn` in a loop, catching the exception and re-raising after the last attempt. Use `functools.wraps(fn)`
on `wrapper` so the name, docstring and signature metadata survive.

??* d3 [python, pytorch] | What is the GIL, and how does it affect PyTorch data loading?
The Global Interpreter Lock lets only one thread execute Python bytecode at a time in CPython. Threads therefore
don't speed up CPU-bound Python, only I/O-bound work. C extensions (NumPy, PyTorch kernels) release the GIL
during heavy compute. `DataLoader` uses worker **processes** (`num_workers`) so Python-heavy decoding and
augmentation run in parallel; the cost is pickling samples between processes and higher memory. Use
`pin_memory=True` and `persistent_workers=True` to cut transfer and start-up overhead.

?? d3 [python] | How does `nn.Module` make `model(x)` call `forward`?
`nn.Module` defines `__call__`, which runs registered forward pre-hooks, calls `self.forward(*args)`, then runs
forward hooks (and sets up backward hooks). That's why you should call `model(x)` rather than
`model.forward(x)`: calling `forward` directly skips the hooks.

?? d4 [algorithms] | How do you find the k largest of n numbers efficiently, and what's the complexity?
Keep a min-heap of size k: push each element and pop the smallest when the heap exceeds k. O(n log k) time and
O(k) memory, and it works on streams. Alternatives: full sort O(n log n); quickselect O(n) average but not
streaming. In PyTorch use `torch.topk`, which is what top-k sampling and MoE routing call.

??* d4 [algorithms, numerics] | Why is the naive formula Var = E[x²] − E[x]² numerically dangerous, and what do you use instead?
When the mean is large relative to the spread, E[x²] and E[x]² are two large, nearly equal numbers;
subtracting them cancels most significant digits (catastrophic cancellation), and in float32 can even give a
negative variance. Welford's online algorithm updates the mean and the sum of squared deviations incrementally
and stays stable. The same issue is why LayerNorm/BatchNorm kernels use Welford or two-pass reductions.

??* d5 [ml-basics] | Explain the bias–variance trade-off with a concrete example.
Expected squared error = bias² + variance + irreducible noise. A degree-1 polynomial fitted to a sine wave has
high bias (systematically wrong) but low variance (similar fit on any sample). A degree-15 polynomial has low
bias but high variance: it chases the noise and changes wildly between samples. Regularisation, more data,
ensembling (bagging lowers variance) and early stopping move you along the trade-off. Very large networks can
show double descent, where test error drops again past the interpolation threshold.

??* d5 [ml-basics] | Give three examples of data leakage and how to prevent them.
(1) Fitting normalisation/feature scaling on the full dataset before splitting — fit on train only, and apply
it inside the CV fold. (2) The same speaker, recording session or patient appearing in both train and test —
split by group. (3) A feature that is a proxy for the label or is only known after the event (e.g. a
"refund issued" flag when predicting fraud). Also: time-series shuffled across the split, and duplicates or
near-duplicates (or augmented copies) on both sides. Prevent with group/time splits, pipelines that fit
transforms per fold, and dedup checks.
