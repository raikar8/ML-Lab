## D1 · Data pipelines: Dataset, DataLoader, collate and sampling

* **Map-style `Dataset`:** `__len__` + `__getitem__(i)`; supports shuffling and random access.
* **`IterableDataset`:** `__iter__` for streams (sharded tar files, WebDataset, live feeds). With multiple workers
  each worker gets a copy — shard by `torch.utils.data.get_worker_info()` or you'll yield duplicates.
* **`DataLoader`:** batching, shuffling (via a `Sampler`), `num_workers` processes, `collate_fn`, `pin_memory`
  (page-locked host memory → faster, async `.to(device, non_blocking=True)`), `prefetch_factor`,
  `persistent_workers`, `drop_last`.

**Variable-length sequences (audio/text):** a custom `collate_fn` pads to the longest item in the batch and returns
**lengths** and/or a boolean **mask**. Loss and pooling must ignore padding (masked mean, `ignore_index` in
cross-entropy, `pack_padded_sequence` for RNNs, `key_padding_mask` for attention).

**Bucketing:** sort (or group) by length so batches contain similar lengths → far less padding. A
`BatchSampler` that shuffles within buckets, then shuffles bucket order, keeps randomness. Alternatively build
batches by a **token/frame budget** instead of a fixed count.

**Worker pitfalls:** every worker inherits the same NumPy RNG seed unless you seed in `worker_init_fn` (augmentation
duplicates — a classic bug, partly fixed in newer PyTorch for torch RNG but not for NumPy/random); large Python
objects in the dataset get copied-on-access in each worker (memory blow-up) — store data in NumPy arrays or memory-
mapped files.

**Is the pipeline the bottleneck?** Time an epoch with the model replaced by a no-op; watch GPU utilisation. If data
loading dominates: more workers, cheaper decoding (precomputed features), caching, moving augmentation to GPU.

> **Interview angle.** Write a padding collate function returning `(x_padded, lengths, mask)` and show how the
> mask is used in a masked mean loss — 10 minutes, very common.

## D2 · `nn.Module` internals, parameters, buffers and hooks

* Assigning an `nn.Parameter` or `nn.Module` as an attribute **registers** it (via `__setattr__`), so it appears
  in `parameters()`, `state_dict()`, moves with `.to()`.
* **Buffers** (`register_buffer`) are state that isn't trained: BatchNorm running stats, RoPE frequency tables,
  causal masks, quantisation scales. They move with the module and are saved in `state_dict` (unless
  `persistent=False`).
* Plain Python lists of modules are **not** registered — use `nn.ModuleList`/`nn.ModuleDict`. A forgotten
  `ModuleList` means those layers aren't trained or moved to GPU.
* `model.train()` / `model.eval()` set `self.training` recursively; dropout and BN read it.
* `state_dict()` / `load_state_dict(strict=...)`: key mismatches after refactors; `strict=False` silently ignores
  missing keys — always print the returned `missing_keys`/`unexpected_keys`.
* **Hooks:** `register_forward_hook(fn(module, inp, out))` for activation capture, feature extraction, collecting
  min/max for quantisation calibration; `register_forward_pre_hook`; full backward hooks for gradient inspection.
  Remove hooks via the returned handle.
* **Parametrisations** (`torch.nn.utils.parametrize`) compute a weight from underlying parameters on access —
  weight norm, spectral norm, orthogonal, pruning masks, LoRA-style reparameterisation.
* **Initialisation:** `module.apply(init_fn)`; `reset_parameters()` conventions.
* **Meta device:** `with torch.device("meta"):` constructs a model without allocating memory — useful to count
  parameters of huge models or materialise shards lazily.

> **Interview angle.** "Count the parameters of this model and how many are trainable" →
> `sum(p.numel() for p in m.parameters() if p.requires_grad)`, and mention tied weights are counted once by
> `parameters()` (de-duplicated).

## D3 · A robust training loop

The skeleton (and what each line protects against):

```python
model.train()
for step, (x, y) in enumerate(loader):
    x, y = x.to(dev, non_blocking=True), y.to(dev, non_blocking=True)
    with torch.autocast(device_type=dev.type, dtype=torch.bfloat16):
        loss = loss_fn(model(x), y) / accum
    loss.backward()                       # (fp16: scaler.scale(loss).backward())
    if (step + 1) % accum == 0:
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # (fp16: scaler.unscale_ first)
        opt.step(); sched.step(); opt.zero_grad(set_to_none=True)
        ema.update(model)
```

* **Gradient accumulation:** divide the loss by `accum` so gradients match a large batch.
* **Evaluation:** `model.eval()` + `torch.inference_mode()`; restore `model.train()` after.
* **Checkpoint everything needed to resume:** model, optimiser, scheduler, scaler, step, epoch, RNG states, config
  and code version; save atomically (write to temp, then rename).
* **Early stopping & best-checkpoint selection** on a validation metric, not training loss.
* **Logging:** loss, LR, grad norm, throughput (samples/s), memory; a few qualitative samples (audio clips!).
* **Reproducibility:** seed everything, `torch.use_deterministic_algorithms(True)` when debugging, note that some
  CUDA ops are non-deterministic and that results can differ across GPUs/library versions.

> **Interview angle.** You'll often be asked to "write a training loop" live. Say what each line is for, include
> `zero_grad`, `eval()`/`train()` switching, `no_grad` for validation, and gradient clipping.

## D4 · Performance: profiling, torch.compile and common slowdowns

**Measure correctly.** CUDA is asynchronous: call `torch.cuda.synchronize()` before reading a timer, warm up
first, and use `torch.utils.benchmark` or `torch.profiler` (CPU/CUDA time per op, memory, traces viewable in
Perfetto/TensorBoard).

**Common slowdowns:**

* Host–device synchronisation: `.item()`, `.cpu()`, printing tensors, `if tensor:` inside the loop.
* Many tiny kernels (element-wise chains) → kernel-launch and memory-bandwidth bound → fuse them.
* Data loading (see D1), small batch sizes, CPU-side Python overhead.
* Non-contiguous tensors or layout conversions; for CNNs on GPU, `channels_last` memory format helps Tensor Cores.
* Not using mixed precision; recomputing masks/positional tables every step instead of buffers.

**`torch.compile`:** TorchDynamo captures Python bytecode into FX graphs (guarding on shapes/dtypes, inserting
**graph breaks** for unsupported Python), AOTAutograd traces the backward, and **Inductor** generates fused Triton
(GPU) or C++/OpenMP (CPU) kernels. Typical gains 1.3–2× for training. Pitfalls: recompilation on changing shapes
(use `dynamic=True` or pad to buckets), graph breaks from `.item()`/data-dependent control flow (check with
`TORCH_LOGS=graph_breaks`), long first-step compile time. `mode="reduce-overhead"` adds CUDA graphs (great for
small-batch inference, needs static shapes); `"max-autotune"` searches kernel configs.

**`torch.export`** produces a full, graph-break-free program for deployment — the entry point to ExecuTorch and
other edge toolchains (week 24).

> **Interview angle.** "Your GPU utilisation is 30%" — profile: is it data loading (CPU busy, GPU idle gaps),
> launch overhead (many short kernels), synchronisation points, or small batches? Fixes map one-to-one.

## D5 · Debugging and testing ML code

**The "overfit one batch" test:** a correct model + loss + optimiser must drive training loss near zero on a single
small batch. If not, there's a bug, not a modelling problem.

**Checklist of the bugs interviewers plant in "find the bug" questions:**

1. Missing `optimizer.zero_grad()` (gradients accumulate forever).
2. `softmax` before `CrossEntropyLoss`, or `sigmoid` before `BCEWithLogitsLoss`.
3. Forgetting `model.eval()` (dropout/BN) or `torch.no_grad()` in validation (memory grows).
4. Broadcasting shape mismatch in the loss (`(B,1)` vs `(B,)`).
5. Wrong axis in softmax/mean (`dim=0` vs `dim=-1`).
6. Attention mask with inverted semantics (True = keep vs True = mask) or a missing causal mask.
7. Data and labels shuffled independently; label leakage through normalisation.
8. `loss` accumulated as a tensor for logging (`total += loss` keeps the graph) → use `loss.item()`.
9. Learning-rate scheduler stepped per epoch when it expects per step (or vice versa).
10. In-place modification of a tensor needed for backward; `.data` misuse.
11. Integer division / dtype issues (`uint8` audio, `int64` targets for CE, `float` targets for BCE).
12. Padding included in loss or pooling.

**Testing layers:** shape tests; equivalence tests against a reference (your attention vs
`F.scaled_dot_product_attention`); `gradcheck` in float64; invariance tests (permutation, padding invariance);
streaming == offline tests; determinism tests. Keep these in `pytest` — the exercises in this app are exactly that
style.

**Monitoring during training:** per-layer gradient norms, activation statistics (dead ReLUs, saturation),
weight-update ratio $\|\Delta W\|/\|W\|\approx10^{-3}$, loss on a fixed validation batch.

> **Interview angle.** When given broken code, first run it on a tiny batch and check shapes and the loss value at
> init (≈ $\log K$ for K-class CE with random init — a great sanity check).

## Questions

??* d1 [pytorch, data] | How do you batch variable-length audio clips efficiently?
Use a custom collate_fn that pads each batch to its longest item and returns lengths and a padding mask, so losses,
pooling, RNN packing and attention can ignore padding. Reduce padding with length bucketing (group similar lengths,
shuffle within buckets and across bucket order) or dynamic batches by a total-frame budget. Optionally precompute
features, use multiple workers with pin_memory, and crop/chunk very long clips.

?? d1 [pytorch, data] | What goes wrong with random augmentation in DataLoader workers, and how do you fix it?
Each worker process is forked with the same Python/NumPy RNG state, so workers can produce identical "random"
augmentations. PyTorch reseeds its own RNG per worker, but NumPy and `random` must be seeded in worker_init_fn
(e.g. from torch.initial_seed()), or use torch's RNG / a Generator for augmentation. Also, IterableDatasets must shard
data by worker id or every worker yields the full stream.

??* d2 [pytorch] | What's the difference between a parameter and a buffer? Give examples of buffers.
Parameters are tensors the optimiser updates (registered via nn.Parameter, requires_grad=True). Buffers are module
state that should move with the model and (usually) be saved in state_dict but not be trained: BatchNorm running
mean/var and step count, precomputed RoPE cos/sin tables, causal masks, quantisation scales and zero-points, EMA
copies. Use register_buffer(name, tensor, persistent=...).

?? d2 [pytorch] | Why must you use nn.ModuleList instead of a Python list for sub-layers?
Module registration happens in nn.Module.__setattr__ for Parameter/Module values; a plain list isn't a Module, so the
layers inside aren't registered: their parameters are missing from parameters() (not trained), state_dict (not
saved) and .to(device) (stay on CPU), and train()/eval() doesn't reach them.

??* d3 [pytorch, training] | Write the key lines of a training step with gradient accumulation and mixed precision, and explain each.
Under autocast(bf16) compute loss = criterion(model(x), y)/accum_steps (scale so the summed gradient equals the
large-batch mean); loss.backward() accumulates into .grad. Every accum_steps: clip_grad_norm_ (after
scaler.unscale_ if using fp16 GradScaler), optimizer.step() (scaler.step), scheduler.step(), optimizer.zero_grad(
set_to_none=True), update EMA. Validation under model.eval() + inference_mode, then model.train(). Log loss.item(),
not the tensor.

?? d3 [pytorch, training] | What must a checkpoint contain to resume training exactly?
Model state_dict, optimiser state (Adam moments), LR scheduler state, GradScaler state, step/epoch counters, the
data-loader position or sampler state (epoch seed), RNG states (Python, NumPy, torch CPU and CUDA), EMA weights, and
the config plus code version. Save atomically to avoid corrupt files on crash.

??* d4 [pytorch, performance] | How does torch.compile work, and what are graph breaks?
TorchDynamo hooks Python's frame evaluation, traces tensor operations into an FX graph with guards (shapes, dtypes,
globals), and falls back to normal Python where it can't trace — a graph break, e.g. on .item(), print, or
data-dependent control flow — splitting the program into several graphs and losing fusion opportunities. AOTAutograd
derives the backward graph; Inductor lowers both to fused Triton/C++ kernels. Changing input shapes trigger
recompiles unless dynamic shapes are enabled.

?? d4 [pytorch, performance] | Why can timing GPU code with time.time() give wrong results?
CUDA kernel launches are asynchronous: the Python call returns immediately while the GPU works. Without
torch.cuda.synchronize() before stopping the timer you measure launch overhead, and the cost shows up later at some
unrelated sync point (.item(), .cpu()). Also warm up (first calls include cuDNN autotuning, allocation, compilation),
repeat and take the median; or use torch.utils.benchmark / CUDA events.

??* d5 [debugging] | What sanity checks do you run before training a new model at scale?
Check the initial loss is ≈ log(num_classes) for CE; overfit a single small batch to ~zero loss; verify data and
label pipeline visually/aurally (listen to augmented audio!); check shapes and masks with asserts; confirm metrics on
a known-good baseline; check gradient norms are finite and non-zero for every parameter group; run a short LR sweep;
make sure validation is in eval mode and has no train-set overlap.

?? d5 [debugging] | Find the bug: validation memory grows every epoch until OOM.
Likely the validation loop runs without torch.no_grad()/inference_mode, so graphs are built and kept, or losses are
accumulated as tensors (total += loss) instead of loss.item(), which keeps each graph alive. Other causes: appending
outputs that require grad to a list, or caching tensors on the GPU across epochs.
