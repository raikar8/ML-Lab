## D1 · Exporting models and graph-level optimisation

**`torch.export`** traces a model into an `ExportedProgram`: a full graph (no Python), in the ATen operator dialect, with explicit
inputs/outputs, parameters as inputs, and **dynamic shapes** declared via `Dim` (e.g. variable sequence length). Unlike
`torch.compile`, graph breaks are errors — you must make the model exportable (remove data-dependent Python control flow, use
`torch.cond` or restructure, avoid `.item()`). It's the entry point to ExecuTorch, AOTInductor and PT2E quantisation.

**ONNX:** `torch.onnx.export` (now dynamo-based) produces a portable graph for ONNX Runtime, TensorRT, OpenVINO, vendor tools. Watch
**opset** versions, unsupported ops (custom ops need plugins), dynamic axes, and numerical parity.

**Graph optimisations** done by exporters/compilers:

* **Constant folding** and dead-code elimination.
* **Operator fusion:** conv + BN (fold), conv + bias + ReLU, matmul + bias + GELU, attention patterns → fused SDPA kernels, LayerNorm.
* **Layout transforms:** NCHW (PyTorch default) ↔ NHWC (most mobile/embedded kernels); inserting transposes everywhere kills
  performance — convert once at the boundary.
* **Quantisation lowering:** Q/DQ pairs folded into integer kernels.
* **Memory planning** (week 20) and static allocation.

**Validation:** compare exported outputs with PyTorch on many real inputs (max abs error, cosine similarity, task metric), including
edge cases (silence, clipping, max length). Keep a golden-output test in CI.

> **Interview angle.** "Export fails because of a Python `if` on a tensor value" — rewrite with tensor ops (`torch.where`), move the
> branch outside the model, or use `torch.cond`; for loops over time, export a single step with explicit state (D4).

## D2 · Runtimes and delegates

| Runtime | Targets | Notes |
|---|---|---|
| **ExecuTorch** (PyTorch) | phones, MCUs, DSPs, NPUs | `.pte` program, ahead-of-time memory planning, tiny core runtime; **delegates/backends**: XNNPACK (CPU), Core ML, MPS, Qualcomm QNN, Arm Ethos-U/VGF, Cadence HiFi/Fusion DSPs, MediaTek, Vulkan; 1.x stable since late 2025 |
| **LiteRT** (ex-TFLite) | Android, iOS, embedded Linux | flatbuffer models, GPU and NPU delegates; **LiteRT-LM** for on-device LLMs; **TFLite Micro** for MCUs with CMSIS-NN kernels |
| **ONNX Runtime** | everywhere | execution providers: CPU, CUDA, TensorRT, QNN, OpenVINO, CoreML, DirectML |
| **TensorRT / TensorRT-LLM** | NVIDIA GPUs, Jetson/Orin/Thor | builds optimised engines (fusion, kernel auto-tuning, INT8/FP8 calibration), plugins for custom ops |
| **Compilers** | many | TVM, IREE/MLIR, XLA — compile graphs to device code |
| **Vendor SDKs** | specific SoCs | Qualcomm QNN / AI Hub, NXP eIQ, TI TIDL, Renesas, Cadence NN library |

**Delegation/partitioning:** the runtime splits the graph into subgraphs the accelerator supports; the rest runs on CPU. Every boundary
costs data copies/conversions — a single unsupported op in the middle of the graph can destroy performance. Check the delegate's
**operator coverage** and quantisation scheme before choosing a model architecture.

**Choosing:** what the target vendor supports best; your framework (PyTorch → ExecuTorch is the most direct path now); model type
(LLM-specific runtimes for LLMs); and team/tooling constraints (C++ integration, binary size, licensing, safety certification).

> **Interview angle.** "Your model runs 3× slower after delegating to the NPU" — partitioning into many small subgraphs with CPU
> fallbacks, layout/precision conversions at each boundary, or ops emulated slowly. Inspect the partition report and replace unsupported ops.

## D3 · LLMs on device

**Stacks:** **llama.cpp / GGUF** (CPU SIMD + Metal/Vulkan/CUDA, k-quants, mmap'd weights — the most portable), **MLX** (Apple silicon),
**ExecuTorch LLM** (export with `export_llm`, XNNPACK 8da4w, KV-cache SDPA custom op, Core ML/QNN backends), **LiteRT-LM**, MLC-LLM,
vendor stacks (Qualcomm GenieX/AI Hub, MediaTek NeuroPilot). Ready-made on-device builds exist for small Qwen3.5, Gemma 3/3n, Llama 3.2,
Phi models.

**Typical config for a phone:** 1–4B model, int4 group-wise weights (or QAT'd low-bit), int8 dynamic activations, 8-bit embeddings,
FP16/int8 KV cache with a bounded context (2–8K, sliding window or hybrid linear-attention model), weights memory-mapped from flash.

**Prefill vs decode on heterogeneous SoCs:** NPUs excel at large static matmuls → prefill; decode is bandwidth-bound and NPUs may not be
faster than the CPU/GPU (static-shape limits, KV-cache update overheads, dispatch costs) — measurements in 2026 found NPUs are *not
always* faster at each stage. Many stacks run prefill on the NPU and decode on CPU/GPU, or use NPU with fixed-size chunked graphs.

**Other constraints:** app memory limits (the OS kills large apps), cold-start load time (mmap helps), thermal throttling during long
generations, battery (joules per token), and model download/update size.

**System patterns:** on-device first with cloud fallback for hard queries (router by confidence/complexity); on-device RAG over personal
data for privacy; per-feature LoRA adapters on a shared base model (Apple's approach); structured output for tool/function calling;
speculative decoding with small draft heads.

> **Interview angle.** "Design a private on-device assistant" — model size from RAM and tokens/s targets (bandwidth ÷ bytes/token),
> quantisation scheme, KV budget, prefill/decode placement, cloud fallback policy, adapters, evaluation.

## D4 · Deploying streaming audio models

**Streaming graphs:** export one **frame/chunk step** with **explicit state tensors** as inputs and outputs (conv history buffers, GRU/
LSTM hidden states, KV cache of chunked attention, normalisation statistics). The host keeps the state between calls. Static shapes per
step suit NPUs/DSPs perfectly. Test: running chunk-by-chunk must equal offline causal inference.

**Typical in-car voice front-end on a HiFi DSP or aDSP:** multi-mic capture → **AEC** (adaptive filter, reference from the media/TTS
playback) → **beamforming** / zone selection → **noise suppression** (classic or small int8 DNN) → **wake word** (tiny always-on model) →
on wake, stream audio to ASR on the application processor/NPU (streaming RNN-T/Conformer, or a quantised Whisper-style model for offline
commands) or to the cloud. Each block has its own latency and compute budget.

**DSP-specific concerns:** fixed-point FFT/feature extraction matching training features (front-end mismatch is a silent killer — test
bit-exactness or at least feature parity), int8/int16 kernels from the vendor NN library, LUT activations, block sizes aligned to the
audio framework's period, MIPS and memory budgets shared with other audio processing.

**Automotive realities:** long product lifecycles and OTA updates, wide temperature ranges (thermal throttling), multiple OSs (QNX,
Linux, Android Automotive), hypervisors and separate safety domains, functional-safety processes (ISO 26262) for safety-relevant
functions and cybersecurity requirements (ISO/SAE 21434), and extensive in-vehicle testing across cars, speeds, windows open/closed,
languages and accents.

> **Interview angle.** For your ITU-T-related tuning work, connect it: you know how to measure speech quality in the car (P.863/POLQA,
> ITU-T P.1100/P.1110 hands-free requirements); explain how you'd use those to evaluate an ML-based front-end vs the classic DSP one.

## D5 · Benchmarking, shipping and operating models on devices

**Benchmarking methodology:** fixed inputs; warm-up runs; many iterations; report **p50/p90/p99** latency (not mean), cold-start
(first-inference) time, peak memory, model load time, energy (J per inference or per token), and sustained performance after thermal
saturation; per-layer profiles to find hotspots; control CPU frequency/governors; compare on the actual device and OS version. Public
references: MLPerf Tiny/Mobile/Client.

**CI for models:** gates on accuracy (on curated test sets and slices), latency/memory on device farms, numerical parity of exported
graphs, model size; regression tests for previously fixed failures.

**Shipping and updates:** versioned model artefacts with metadata (training data version, code commit, quantisation config); **OTA**
updates with staged rollout, A/B tests, kill switches and rollback; compatibility between model and app/runtime versions; delta updates
for large models.

**Monitoring on device:** privacy-preserving telemetry (aggregate metrics: wake-word triggers, false-accept reports, confidence
distributions, latency), drift detection, user feedback signals; **shadow mode** for new models (run silently, compare decisions); federated
analytics/learning and on-device personalisation (e.g. speaker adaptation) when raw data can't leave the device.

> **Interview angle.** "How do you know your on-device model is still working six months after launch?" — telemetry on proxy metrics,
> drift detectors on input statistics, targeted data collection with consent, periodic re-evaluation, and a safe OTA path.

## Questions

??* d1 [deployment] | What is torch.export and how does it differ from torch.compile and TorchScript?
torch.export captures the whole model ahead of time into an ExportedProgram — a single graph of ATen ops with explicit parameters, inputs and
declared dynamic shapes — and fails (rather than falling back) on untraceable Python, so the result can run without Python on other runtimes
(ExecuTorch, AOTInductor) and be quantised with PT2E. torch.compile is a just-in-time optimiser for running in Python that tolerates graph breaks.
TorchScript was the older scripting/tracing approach, now in maintenance mode.

?? d1 [deployment] | What graph optimisations do deployment toolchains perform?
Constant folding and dead-code elimination; operator fusion (conv+BN folding, conv/matmul with bias and activation, fused attention and norms);
layout conversion to the backend's preferred format (e.g. NHWC) once at the boundaries; quantisation lowering (folding quantise/dequantise pairs into
integer kernels); shape specialisation; and ahead-of-time memory planning. These remove memory traffic and kernel launches, which dominate cost on
edge devices.

??* d2 [deployment] | How does delegation to an NPU work in runtimes like ExecuTorch or LiteRT, and what can go wrong?
The runtime partitions the graph into subgraphs the accelerator backend supports and compiles them for it; unsupported operators run on the CPU.
Problems: unsupported ops in the middle of the network split it into many partitions, each boundary adding copies, layout and precision conversions
and synchronisation; the NPU may require specific quantisation schemes or static shapes; some ops are emulated slowly. Check operator coverage and
the partition report early, replace unsupported ops with supported equivalents, and benchmark on device.

??* d3 [on-device-llm] | How would you run a 3B-parameter LLM on a phone, and what performance would you expect?
Quantise weights to 4-bit group-wise (AWQ/GPTQ or QAT) with int8 dynamic activations and 8-bit embeddings (~2 GB), memory-map the weights, bound the
KV cache (FP16/int8, 2–8K context, sliding window or a hybrid linear-attention model), and use an optimised runtime (llama.cpp, ExecuTorch with XNNPACK
or the vendor NPU backend, LiteRT-LM). Run prefill on the NPU/GPU where efficient; decode is bandwidth-bound: ~2 GB per token on ~60 GB/s LPDDR gives
an upper bound around 25–30 tokens/s, typically 10–20 in practice, with prefill of hundreds to thousands of tokens/s. Watch memory limits, thermal
throttling and energy per token.

?? d3 [on-device-llm] | Why might the phone NPU not speed up LLM decoding as much as prefill?
Prefill is large static matmuls — what NPUs are designed for. Decode is a sequence of small, memory-bound matrix–vector operations where the limit is
DRAM bandwidth shared by all processors, so extra NPU TOPS don't help; NPUs also often need static shapes (awkward for a growing KV cache), have
dispatch overheads per step, and may lack fast support for the attention/KV-update patterns. Measurements show the CPU or GPU can match or beat the NPU
for decode, so stacks often split phases across processors.

??* d4 [audio, deployment] | How do you deploy a streaming recurrent/causal-conv audio model on a DSP or NPU?
Export a single-step (frame or chunk) graph with fixed shapes whose inputs are the new frame plus all state (conv history buffers, RNN hidden states,
running normalisation stats) and whose outputs are the result plus updated state; the host keeps state between calls. Quantise to the backend's int8/int16
scheme, ensure the feature front-end on the device matches training (bit-exact or verified parity), and test that chunked inference equals offline causal
inference. Measure worst-case per-frame time against the hop size.

?? d4 [automotive] | What makes deploying ML in cars different from phones?
Long lifecycles with OTA updates over many years; wide temperature ranges and thermal limits; heterogeneous SoCs with hypervisors, multiple OSs (QNX, Linux,
Android Automotive) and safety domains; functional-safety (ISO 26262) and cybersecurity (ISO/SAE 21434) processes for relevant functions; strict
latency/robustness requirements for voice and driver monitoring; acoustic variability (speeds, road noise, windows, HVAC, multiple occupants); and the need
for extensive in-vehicle validation across car models, languages and conditions.

??* d5 [benchmarking] | How do you benchmark an on-device model properly?
Use the real device, OS and runtime build; fix inputs and power/thermal conditions; warm up; run many iterations and report p50/p90/p99 latency rather than
the mean; separately measure cold start/model load time, peak memory, and energy per inference or per token; run long enough to capture sustained
performance after thermal throttling; profile per layer to find hotspots and CPU fallbacks; and compare against a baseline under identical conditions.

?? d5 [mlops] | How do you safely update a model on millions of deployed devices?
Version every artefact with its data, code and quantisation config; validate offline (accuracy on slices, latency/memory on a device farm, numerical parity);
optionally run the new model in shadow mode; roll out OTA in stages with A/B comparison of privacy-preserving telemetry (trigger rates, false-accept reports,
latency, crashes); keep kill switches and fast rollback; ensure compatibility with app/runtime versions; and use delta updates to limit download size.
