## D1 · Inference anatomy and the metrics that matter

**Latency metrics:** **TTFT** (time to first token: queueing + prefill), **TPOT / ITL** (time per output token / inter-token
latency: decode), end-to-end latency = TTFT + TPOT × output length. **Throughput:** tokens/s across all users. **Goodput:**
throughput of requests that meet their SLOs. On device you care about TTFT, TPOT, peak memory, energy per token and
thermal throttling.

**Arithmetic intensity** (FLOPs per byte moved) decides the bottleneck. A matmul $(B\times d)\cdot(d\times d)$ in BF16 does
$2Bd^2$ FLOPs and moves ≈ $2d^2$ bytes of weights → intensity ≈ $B$ FLOPs/byte. An H100 needs ~300 FLOPs/byte to be
compute-bound (989 TFLOP/s ÷ 3.35 TB/s); a phone NPU needs ~100–500. So decode at batch 1–32 is **memory-bound**; prefill
(B = many tokens) is compute-bound.

**Levers, grouped by bottleneck:**

* *Bytes of weights:* quantisation (W8A8, W4A16, FP8, FP4), sparsity, smaller/distilled models, MoE (fewer active).
* *Bytes of KV:* GQA/MLA, KV quantisation, eviction, sparse/linear attention.
* *More useful work per byte:* batching, speculative decoding, MTP.
* *Overheads:* fused kernels, CUDA graphs / static graphs, avoiding Python per token, efficient sampling.
* *Scheduling:* continuous batching, chunked prefill, disaggregation, prefix caching.

> **Interview angle.** When asked "how would you speed up inference?", first ask: latency or throughput? which
> phase? what hardware? Then match levers to the bottleneck rather than listing everything.

## D2 · KV-cache management: paged, prefix-shared, quantised, disaggregated

**The problem:** each request's KV cache grows token by token to an unknown final length. Pre-allocating the max wastes
memory (internal fragmentation); naive allocation fragments memory between requests.

**PagedAttention (vLLM):** split the KV cache into fixed-size **blocks** (e.g. 16 tokens), keep a per-sequence **block
table** mapping logical blocks to physical blocks, allocate on demand — like OS virtual memory. Near-zero waste, and blocks
can be **shared** copy-on-write between sequences (parallel sampling, beam search). The attention kernel gathers keys/values
through the block table.

**Prefix caching:** many requests share a prefix (system prompt, few-shot examples, a long document, multi-turn history).
Cache its KV once and reuse it: vLLM's automatic prefix caching (hash of block contents), **SGLang's RadixAttention** (a radix
tree over token prefixes with LRU eviction). Huge TTFT savings for agents and chat.

**KV quantisation:** FP8 KV halves memory with negligible loss; INT4/2-bit KV with per-channel key scales (keys have outlier
channels) and per-token value scales (KIVI). DeepSeek-V4 stores most KV in FP8 with RoPE dims in BF16.

**Offloading and disaggregation:** move cold KV to CPU memory or SSD; **Mooncake** (Moonshot/Kimi's serving platform,
FAST'25 best paper) is built around a distributed **KV-cache store** across GPU/CPU/SSD of the cluster, with prefill and
decode on separate nodes and KV transferred between them.

**On device:** KV cache lives in the same limited RAM as weights; a 3B GQA model (28 layers, 8 KV heads, d_h 128) needs
~112 KB/token in BF16 → 450 MB at 4K tokens. Hence 8-bit/4-bit KV, sliding windows, and hybrid linear-attention models for
on-device long context.

> **Interview angle.** Explain PagedAttention with the OS analogy (pages, page table, copy-on-write) and say what it
> fixes (fragmentation → larger batch → higher throughput), not just what it is.

## D3 · Kernels: FlashAttention, FlashDecoding and fusion

**FlashAttention** computes exact attention without materialising the $T\times T$ matrix in HBM. It tiles Q, K, V into blocks
that fit in on-chip SRAM and uses the **online softmax**: keep a running max $m$ and normaliser $\ell$ per query row, and
rescale the partial output when a new block raises the max:

```math
m'=\max(m,\tilde m),\quad \ell'=e^{m-m'}\ell+e^{\tilde m-m'}\tilde\ell,\quad O'=\frac{e^{m-m'}\ell\,O+e^{\tilde m-m'}\tilde P V_j}{\ell'}
```

HBM traffic drops from $O(T^2)$ to $O(T^2d^2/M)$ (M = SRAM size), memory to $O(T)$; the backward pass **recomputes**
attention from saved $m,\ell$ instead of storing the matrix. It's faster *because* it does more FLOPs but far fewer memory
accesses — the canonical "IO-aware" kernel. FA-2 improved parallelism/work partitioning; **FA-3** uses Hopper features
(asynchronous TMA loads, warp specialisation, FP8). DeepSeek open-sourced **FlashMLA** (decode kernel for MLA) and other
kernels.

**FlashDecoding (split-KV):** at decode there's only one query per sequence, so parallelising over queries leaves the GPU idle
for long contexts; split the KV sequence across thread blocks, compute partial softmax results, and combine them with the
same log-sum-exp rescaling.

**Fusion and graphs:** fuse RMSNorm + matmul + RoPE, the SwiGLU activation, sampling; quantised GEMM kernels that dequantise
in registers (Marlin, Machete for W4A16); **CUDA graphs** capture the whole decode step to remove CPU launch overhead (crucial
at small batch). On edge, the equivalent is a static graph compiled by the runtime (ExecuTorch/LiteRT/QNN) with fused
operators.

## D4 · Batching and scheduling at serving time

* **Static batching:** wait for a batch, run until the longest sequence finishes → GPUs idle on finished slots, high latency.
* **Continuous (in-flight / iteration-level) batching** (Orca, vLLM, TensorRT-LLM, SGLang): the scheduler adds and removes
  sequences **every decode step**. Throughput gains of several × at the same latency.
* **Chunked prefill:** split long prompts into chunks and co-schedule them with decode steps so a big prefill doesn't
  stall everyone's TPOT (Sarathi-Serve).
* **Prefill/decode disaggregation** (DistServe, Splitwise, Mooncake): run prefill and decode on different GPU pools, sized and
  parallelised differently (prefill: tensor parallel, compute-heavy; decode: large batch, memory-heavy), transferring KV
  between them. DeepSeek serves V3/R1 this way, with very wide **expert parallelism** for decode so each GPU hosts few experts
  and batches are large per expert.
* **Scheduling policies:** FCFS vs shortest-job-first approximations, preemption (swap or recompute KV), priority for
  interactive traffic, admission control under memory pressure.
* **Structured output:** constrained decoding with grammars/JSON schemas masks invalid tokens each step (XGrammar, Outlines);
  must be fast enough not to bottleneck decode.

**On device**, batching is usually 1, so the levers are kernel efficiency, quantisation, speculative decoding and avoiding
re-prefill (prefix/KV reuse across turns).

> **Interview angle.** "Throughput doubled but users complain about stutter" → long prefills interrupting decode; fix with
> chunked prefill, separate prefill pool, or priority scheduling.

## D5 · Speculative decoding, MTP drafts and other decode accelerators

**Speculative decoding** (Leviathan et al., Chen et al. 2023): a cheap **draft** model proposes $\gamma$ tokens; the large
**target** model scores all of them in **one** forward pass (it's memory-bound anyway, so verifying $\gamma+1$ positions costs
about the same as generating one). Accept draft token $x$ with probability $\min(1, p(x)/q(x))$; on rejection, sample from the
residual $\mathrm{norm}(\max(0,p-q))$ and stop. This **exactly preserves** the target distribution. With per-token acceptance
rate $\alpha$, expected tokens per target pass:

```math
\mathbb E[\text{tokens}]=\frac{1-\alpha^{\gamma+1}}{1-\alpha}
```

**Draft options:**

* A small model from the same family (needs the same tokenizer).
* **Medusa:** extra decoding heads on the target predicting $t+2, t+3, \dots$; tree-structured verification.
* **EAGLE (1/2/3):** a light autoregressive head over the target's hidden features — high acceptance rates.
* **MTP modules as drafts:** DeepSeek-V3 trains a multi-token-prediction module (sequential, keeps the causal chain) as an
  auxiliary objective; at inference it drafts the next token with ~85–90% acceptance, ≈1.8× tokens/s. Qwen3.5, MiniMax M2,
  GLM and DeepSeek-V4 also ship MTP heads.
* **Prompt lookup / n-gram drafting:** copy candidate continuations from the prompt — great for editing and RAG.
* **Self-speculation:** skip layers of the target to draft (LayerSkip).

**On device**, speculative decoding is attractive because decode is bandwidth-bound and NPUs have spare compute, but the draft
model also costs memory — MTP heads/EAGLE heads are cheap in memory, which is why they suit edge.

> **Interview angle.** Prove (or at least explain) why speculative sampling is lossless: the acceptance + residual sampling
> construction makes the marginal distribution of each emitted token exactly $p$.

## Questions

??* d1 [inference] | What are TTFT and TPOT, and which optimisations target each?
TTFT (time to first token) = queueing + prefill of the prompt; it's compute-bound and improved by faster prefill kernels
(FlashAttention), prefix caching, chunked/parallel prefill, tensor parallelism and smaller prompts. TPOT (time per output
token) is decode; it's memory-bandwidth bound and improved by weight/KV quantisation, GQA/MLA, speculative decoding, CUDA
graphs/fused kernels, and avoiding prefill interference (chunked prefill or disaggregation). Throughput is improved by
batching, which can hurt both if overdone.

??* d2 [kv-cache, serving] | Explain PagedAttention and why it increases throughput.
The KV cache is divided into fixed-size blocks allocated on demand and mapped through a per-sequence block table, like
virtual-memory pages. This eliminates reserving max-length buffers and external fragmentation, so near-100% of KV memory
holds real tokens; more sequences fit, so batches are larger and throughput higher. Blocks can be shared copy-on-write for
parallel sampling/beam search and prefix sharing. The attention kernel reads K/V via the block table.

?? d2 [kv-cache, serving] | What is prefix caching and when does it help most?
Reusing the computed KV cache for a token prefix shared across requests (system prompt, tools, few-shot examples, documents,
earlier turns), so only the new suffix needs prefill. It slashes TTFT and compute for chat, agents with long tool
descriptions, and RAG over repeated documents. Implementations hash KV blocks (vLLM) or keep a radix tree of prefixes with
LRU eviction (SGLang RadixAttention). It doesn't help unique prompts.

??* d3 [kernels] | How does FlashAttention compute exact attention without storing the T×T matrix?
It tiles queries and keys/values into blocks that fit in on-chip SRAM. For each query block it streams through K/V blocks,
computing local scores and maintaining a running row max m and normaliser ℓ (online softmax); when a block raises the max, the
accumulated output and ℓ are rescaled by exp(m_old − m_new). After all blocks, dividing by ℓ gives the exact softmax-weighted
sum. Only O(T) statistics are stored; the backward pass recomputes scores block by block. It's faster because HBM traffic, not
FLOPs, was the bottleneck.

?? d3 [kernels] | What problem does FlashDecoding solve?
In decode each sequence has a single query, so FlashAttention's parallelisation over query blocks gives too little work to
fill the GPU when batch is small and context long. FlashDecoding splits the KV cache along the sequence across many thread
blocks, computes partial attention outputs with their max and sum, and merges them with log-sum-exp rescaling — making
long-context, small-batch decoding much faster.

??* d4 [serving] | What is continuous batching and why is it better than static batching for LLMs?
Static batching runs a fixed batch until the longest sequence finishes, so slots of finished sequences sit idle and new
requests wait. Continuous (iteration-level) batching re-forms the batch at every decode step: finished sequences leave, new
ones join (after their prefill), keeping the GPU full. Output lengths vary widely, so this gives several-fold higher
throughput at equal or lower latency. It requires dynamic KV management, which PagedAttention provides.

?? d4 [serving] | Why separate prefill and decode onto different machines?
They have different bottlenecks and SLOs: prefill is compute-bound and bursty, decode is memory-bound and latency-sensitive.
Co-locating them makes long prefills stall decode steps (TPOT spikes) and forces one parallelism configuration on both.
Disaggregation lets each pool be sized and parallelised for its phase (e.g. TP for prefill, large-batch wide expert
parallelism for decode) at the cost of transferring the KV cache between pools. DeepSeek and Mooncake (Kimi) serve this way.

??* d5 [speculative] | How does speculative decoding work and why is it lossless?
A draft model proposes γ tokens autoregressively with probabilities q; the target computes its probabilities p for all of
them in one forward pass. Each token x is accepted with probability min(1, p(x)/q(x)); at the first rejection, a replacement is
sampled from norm(max(0, p − q)) and the rest are discarded; if all are accepted, one extra token is sampled from p. The
probability of emitting x is q(x)·min(1, p/q) + (rejection mass)·residual(x) = p(x), so the output distribution equals the
target's. Speed-up comes from the target verifying several tokens per memory-bound pass.

?? d5 [speculative, chinese-models] | How does DeepSeek use its MTP module for faster inference?
During training, sequential multi-token-prediction modules predict additional future tokens (keeping the causal chain by
feeding the previous depth's representation), densifying the training signal. At inference the MTP module acts as a built-in
draft for speculative decoding: it proposes the next token, the main model verifies; DeepSeek reported ~85–90% acceptance for
the second token, ≈1.8× generation speed. Because it shares the embedding and head with the main model, it adds little memory.

?? d5 [speculative] | What determines the speed-up of speculative decoding?
The acceptance rate α (how well the draft matches the target), the draft length γ, and the relative cost c of a draft step vs a
target step. Expected tokens per target pass = (1 − α^{γ+1})/(1 − α); the speed-up ≈ that divided by (1 + γc). It helps most when
decode is memory-bound (small batch) and the draft is cheap and well aligned; at large batch sizes the target becomes
compute-bound and verification is no longer free, so gains shrink.
