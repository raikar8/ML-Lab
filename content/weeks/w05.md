## D1 · Computational graphs and reverse-mode autodiff

A program that computes a loss is a directed acyclic graph of primitive ops. Automatic differentiation applies
the chain rule over that graph **exactly** (not numerically, not symbolically).

**Forward mode** propagates tangents alongside values: one pass gives a Jacobian–vector product $Jv$, i.e. the
derivative of all outputs w.r.t. one input direction. **Reverse mode** runs the program forward, stores
intermediates, then propagates adjoints $\bar v = \partial L/\partial v$ backwards: one pass gives a
vector–Jacobian product $u^\top J$, i.e. the gradient of one scalar w.r.t. **all** inputs.

For a scalar loss and millions of parameters, reverse mode costs a small constant times the forward pass —
that's backpropagation. Forward mode would need one pass per parameter.

For each node $v = f(u_1,\dots,u_k)$, reverse mode accumulates:

```math
\bar u_i \mathrel{+}= \bar v\,\frac{\partial f}{\partial u_i}
```

The `+=` matters: when a value is used in several places (a residual connection, a shared embedding), its
gradient is the **sum** over its uses.

**Memory.** Reverse mode must keep the forward activations needed by each backward rule. Activation memory
scales with batch × sequence × depth and usually dominates training memory — hence activation checkpointing
(recompute instead of store, week 9/15) and why inference (no backward) needs far less memory.

**Topological order.** Backward visits nodes in reverse topological order so a node's adjoint is complete before
it's propagated further. A ~100-line scalar engine (Karpathy's *micrograd*) is a classic take-home; you'll build
one today.

> **Interview angle.** "Why reverse mode for neural nets?" — cost is proportional to the number of outputs
> (1 loss) not inputs (millions of parameters). Forward mode is better for few inputs/many outputs, e.g.
> sensitivity analysis or Jacobian-vector products in some second-order methods.

## D2 · Backprop through an MLP with matrix shapes

For a batch $X\in\mathbb R^{B\times d}$, a linear layer $Y = XW + b$ with $W\in\mathbb R^{d\times h}$. Given
the upstream gradient $\bar Y\in\mathbb R^{B\times h}$:

```math
\bar W = X^\top\bar Y,\qquad \bar b = \textstyle\sum_{\text{batch}}\bar Y,\qquad \bar X = \bar Y W^\top
```

A reliable trick: the gradient of a tensor always has **that tensor's shape**, so there is usually only one way
to multiply the available matrices to get it.

**Element-wise activations:** $\bar Z = \bar A\odot f'(Z)$. ReLU: mask by $Z>0$. Sigmoid:
$\sigma(1-\sigma)$. Tanh: $1-\tanh^2$.

**Softmax + cross-entropy** (fused): $\bar Z = (P - Y_{\text{onehot}})/B$ for a mean-reduced loss.

**Gradient checking:** compare analytic gradients with central differences
$\frac{f(x+\epsilon)-f(x-\epsilon)}{2\epsilon}$ (error $O(\epsilon^2)$) in **float64**, using relative error
$\frac{|a-n|}{\max(|a|,|n|)}$; ~1e-7 is good. `torch.autograd.gradcheck` does this for you.

**Batch-norm backward**, attention backward and conv backward are the same idea with more bookkeeping; conv
backward w.r.t. input is a (transposed) convolution, and w.r.t. weights is a correlation of input and output
gradients.

> **Interview angle.** You may be asked to implement a 2-layer MLP with manual backward in NumPy in ~30 minutes.
> Write the forward pass caching what backward needs, then go layer by layer from the loss, checking shapes.

## D3 · Activations, initialisation and vanishing/exploding gradients

**Why initialisation matters.** In a deep stack, the forward signal and the backward gradient are products of
many Jacobians. If each layer scales variance by $\alpha$, after $L$ layers it's $\alpha^L$: it vanishes or
explodes unless $\alpha\approx1$.

For $y=Wx$ with $n_{in}$ inputs, i.i.d. zero-mean weights of variance $\sigma^2$ give
$\mathrm{Var}(y)=n_{in}\sigma^2\mathrm{Var}(x)$. Choose $\sigma^2$ to keep it constant:

```math
\text{Xavier/Glorot: }\sigma^2=\frac{2}{n_{in}+n_{out}}\ (\tanh)\qquad \text{He/Kaiming: }\sigma^2=\frac{2}{n_{in}}\ (\text{ReLU, which zeros half the units})
```

**Activations:**

* Sigmoid/tanh saturate → gradients near zero; sigmoid isn't zero-centred.
* **ReLU**: cheap, no saturation for $x>0$, but "dead" units if they get stuck negative.
* Leaky ReLU / PReLU: small negative slope.
* **GELU** $x\Phi(x)$ and **SiLU/Swish** $x\sigma(x)$: smooth, standard in transformers.
* **GLU variants** (SwiGLU): $\big(\mathrm{SiLU}(xW_1)\odot xW_3\big)W_2$ — the FFN in Llama, Qwen, DeepSeek.
  Gating adds a multiplicative interaction; to keep params equal, the hidden size is $\tfrac{2}{3}\cdot4d$.

**Fixes for depth:** residual connections give every layer an identity path, so the Jacobian is $I + \partial F$
and gradients flow even when $\partial F$ is small; normalisation layers keep activations in range; gradient
clipping stops explosions (RNNs, transformers); careful init of the last layer in each residual branch (zero or
scaled by $1/\sqrt{2L}$, as in GPT-2) keeps the residual stream stable at init.

> **Interview angle.** "Why can't you initialise all weights to zero?" — symmetry: every unit in a layer gets
> the same gradient and stays identical forever. Biases can be zero.

## D4 · PyTorch tensors: storage, strides, views and broadcasting

A tensor is a view onto a 1-D **storage** with a `shape`, `stride` (elements to skip per dimension), `offset`
and `dtype`. A contiguous $(3,4)$ float tensor has stride $(4,1)$.

* **Views** (no copy): `view`, slicing, `transpose`/`permute`, `expand`, `unsqueeze`, `as_strided`, `unfold`.
* `transpose` makes a tensor **non-contiguous**; `view` then fails and you need `reshape` (copies if needed) or
  `.contiguous()`. Many kernels are faster on contiguous memory.
* `expand` creates stride-0 dimensions: a broadcasted view that uses no memory. Writing into it in place is an
  error — many logical elements share one memory location.

**Broadcasting rules:** align shapes from the right; dimensions are compatible if equal or one of them is 1;
missing leading dimensions are treated as 1. Classic bug: `(B,)` minus `(B,1)` gives `(B,B)`, silently.

**einsum** expresses most tensor contractions clearly: attention scores `einsum('bhqd,bhkd->bhqk', q, k)`,
batched matmul `bij,bjk->bik`. Good for interviews because it's self-documenting.

**In-place ops** (`x.add_(1)`, `x[...] = 0`) save memory but can break autograd: each tensor has a version
counter, and if a value saved for backward was modified in place you get *"one of the variables needed for
gradient computation has been modified by an inplace operation"*.

**dtype and device:** operations need matching devices; mixed dtypes follow type promotion. `.to()` returns
the same tensor if nothing changes, otherwise a copy. Moving tensors CPU↔GPU synchronises.

**Framing audio with strides:** `x.unfold(-1, size=frame, step=hop)` (or `as_strided`) gives an
`(n_frames, frame)` view with zero copy — a nice thing to show in an audio-ML interview.

> **Interview angle.** Explain `view` vs `reshape` vs `contiguous()` precisely; it comes up whenever you write
> multi-head attention (`(B,T,H*D) → (B,H,T,D)` needs a transpose).

## D5 · Autograd internals and custom Functions

* A tensor with `requires_grad=True` created by the user is a **leaf**; results of ops on it have a
  `grad_fn` (a node in the backward graph). Only leaves get `.grad` populated by default
  (`retain_grad()` for non-leaves).
* `loss.backward()` traverses the graph; **gradients accumulate** into `.grad` — hence
  `optimizer.zero_grad()` (with `set_to_none=True`, the default, which also saves memory). Accumulation is also
  what makes gradient accumulation over micro-batches work.
* The graph is freed after backward; `retain_graph=True` keeps it for a second backward.
  `create_graph=True` builds a graph of the backward itself for higher-order gradients (gradient penalties, MAML).
* `torch.no_grad()` stops recording; `torch.inference_mode()` also skips version-counter bookkeeping and is
  faster for pure inference; `detach()` returns a tensor that shares data but has no history.

**Custom `torch.autograd.Function`:** define `forward(ctx, ...)` and `backward(ctx, grad_out)`, save tensors with
`ctx.save_for_backward`. Uses: numerically stable or memory-saving backward rules, the
**straight-through estimator** for quantisation (`forward` rounds, `backward` passes the gradient through as if
it were identity — you'll use this in week 22 for QAT), gradient reversal for domain adaptation, fused kernels.

**Hooks:** `tensor.register_hook(fn)` sees/modifies a gradient; module forward hooks capture activations;
`register_full_backward_hook` sees module gradients. Used for feature extraction, gradient clipping per layer,
activation statistics for quantisation calibration.

> **Interview angle.** "Your loss decreases but one sub-module's weights never change" → it's under `no_grad`,
> it was `detach()`ed, its params aren't in the optimizer, `requires_grad=False`, or an integer/argmax op broke
> the graph.

## Questions

??* d1 [autodiff] | Why does deep learning use reverse-mode automatic differentiation rather than forward mode?
Reverse mode computes a vector–Jacobian product: one backward pass yields the gradient of a scalar output w.r.t.
every input, at a small constant multiple of the forward cost. Forward mode computes Jacobian–vector products,
needing one pass per input direction. With one scalar loss and millions of parameters, reverse mode is millions
of times cheaper. The price is memory: reverse mode must store forward intermediates.

?? d1 [autodiff] | Why is the gradient of a value used in two places the sum of the two contributions?
By the multivariable chain rule, if L depends on v through paths u₁ and u₂, then ∂L/∂v = Σᵢ ∂L/∂uᵢ · ∂uᵢ/∂v. Autograd
implements this by accumulating (+=) adjoints. It's why residual connections pass the upstream gradient straight
through, and why tied input/output embeddings receive gradient from both uses.

??* d2 [backprop] | For Y = XW + b, give the gradients with respect to X, W and b.
With upstream gradient G = ∂L/∂Y of shape (B,h): ∂L/∂W = XᵀG (d,h), ∂L/∂b = G summed over the batch (h,),
∂L/∂X = GWᵀ (B,d). Shapes force the order: each gradient has the shape of the tensor it's for.

?? d2 [backprop] | How do you gradient-check an implementation, and what pitfalls are there?
Compare analytic gradients with central finite differences (f(x+ε)−f(x−ε))/2ε, in float64, with ε≈1e-5–1e-6,
using relative error. Pitfalls: float32 precision, kinks (ReLU at 0, max) giving spurious mismatches,
randomness (dropout) changing between evaluations, and checking only a few random coordinates of large tensors.

??* d3 [initialisation] | Derive He initialisation.
For y = Σᵢ wᵢxᵢ with n_in inputs, zero-mean independent weights, Var(y) = n_in Var(w) E[x²]. With ReLU on the
previous layer's zero-mean symmetric pre-activations, E[x²] = ½ Var(pre-activation). To keep the
pre-activation variance constant across layers, n_in Var(w) · ½ = 1, so Var(w) = 2/n_in. Xavier instead balances
forward and backward variance for linear/tanh units: 2/(n_in+n_out).

??* d3 [architecture] | Why do residual connections help train very deep networks?
The block computes x + F(x), so its Jacobian is I + ∂F/∂x. The identity term gives gradients a direct path to
early layers regardless of depth, preventing vanishing gradients, and at initialisation the network is close to
identity, which is easy to optimise. They also smooth the loss landscape, and let a block learn a small
correction rather than a full transformation. Modern variants (hyper-connections, DeepSeek's mHC, Kimi's
Attention Residuals) generalise how this residual stream is mixed.

?? d3 [activations] | What is SwiGLU and why do modern LLMs use it?
FFN(x) = (SiLU(xW₁) ⊙ xW₃)W₂: a gated linear unit with a Swish gate. The multiplicative gate lets the network
modulate features per token, and empirically it gives lower perplexity than ReLU/GELU FFNs at the same compute
(Shazeer 2020). Because it has three matrices instead of two, the hidden width is usually ~(2/3)·4d (e.g.
8/3·d) to keep the parameter count equal.

??* d4 [pytorch] | What's the difference between view, reshape and contiguous in PyTorch?
`view` reinterprets the same storage with a new shape; it requires compatible strides (typically contiguous) and
never copies. `reshape` returns a view when possible and silently copies otherwise. `contiguous()` returns a
tensor laid out in row-major order, copying if it wasn't. After `transpose`/`permute`, `view` fails; use
`reshape` or `.contiguous().view(...)`.

?? d4 [pytorch] | Explain PyTorch broadcasting and a bug it can cause.
Shapes are aligned from the trailing dimension; each pair must be equal or one of them 1, and missing dimensions
count as 1; size-1 dims are virtually expanded (stride 0, no copy). Bug: predictions of shape (B,1) minus targets
of shape (B,) broadcast to (B,B), so an MSE loss averages over B² wrong pairs without any error. Assert shapes or
squeeze explicitly.

??* d5 [autograd] | What is a leaf tensor, and why do gradients accumulate in .grad?
A leaf is a tensor not produced by a recorded op — usually a parameter or input created with requires_grad=True.
Autograd populates .grad only for leaves (by default). Gradients are added, not overwritten, because a leaf may
receive gradient from several backward calls; this enables gradient accumulation across micro-batches, but it
means you must zero gradients each optimiser step.

??* d5 [autograd, quantization] | Write (in words) a custom autograd Function for the straight-through estimator.
forward(ctx, x): return round(x) (or a quantise-dequantise). backward(ctx, g): return g unchanged (optionally
zero it where x was outside the clipping range, i.e. the clipped STE). Rounding has zero gradient almost
everywhere, so without STE no gradient reaches the weights; STE pretends the rounding is identity in the backward
pass. This is the basis of quantisation-aware training and of binary/ternary networks.

?? d5 [autograd] | What's the difference between torch.no_grad() and torch.inference_mode()?
Both stop building the autograd graph. inference_mode additionally disables view tracking and version-counter
bumps, so it's slightly faster and uses less memory, but tensors created inside it can't be used later in
autograd-recorded computations. Use inference_mode for pure inference/serving, no_grad for things like evaluation
inside training or updating EMA weights.
