## D1 · Framing: the retrieval → ranking → re-ranking funnel

A recommender chooses a few items from millions for each request within ~100 ms, so it's built as a **funnel**:

1. **Candidate generation / retrieval** (millions → ~1,000): cheap models — two-tower embeddings + approximate nearest-neighbour
   search, co-visitation graphs, popularity, the user's recent items. Optimise **recall@k**.
2. **Ranking** (~1,000 → ~100): a heavier model with rich user, item and context features and their interactions, predicting
   calibrated probabilities of engagement events (click, watch time, purchase). Optimise ranking metrics and calibration.
3. **Re-ranking / policy** (~100 → ~10): business rules, diversity, freshness, de-duplication, fairness and exploration.

**Feedback types:** explicit (ratings) is rare; **implicit** (clicks, dwell, purchases) is abundant but noisy and biased — a
non-click doesn't mean dislike (maybe the item wasn't seen).

**Metrics:** offline — recall@k / hit-rate for retrieval; NDCG@k, MAP, AUC and log-loss/calibration for ranking; coverage, diversity,
novelty. Online — A/B tests on long-term metrics (retention, satisfaction), not only short-term clicks. Offline–online mismatch is
the norm: logged data reflects the old system's choices.

> **Interview angle.** Start every recsys design by drawing the funnel with the candidate counts and latency budget per stage —
> then say which objective each stage optimises.

## D2 · Collaborative filtering and matrix factorisation

Represent users and items in a shared latent space: predict $\hat r_{ui}=\mu+b_u+b_i+p_u^\top q_i$ and minimise

```math
\sum_{(u,i)\in\mathcal O}\big(r_{ui}-\hat r_{ui}\big)^2+\lambda\big(\|p_u\|^2+\|q_i\|^2+b_u^2+b_i^2\big)
```

* **SGD**: loop over observed pairs, update $p_u, q_i$ with the error — simple, handles biases.
* **ALS**: fix $Q$, each $p_u$ is a ridge-regression solution; alternate — parallelisable, good for implicit data.
* **Implicit feedback** (Hu, Koren & Volinsky): treat all pairs as observed with preference $p_{ui}\in\{0,1\}$ and confidence
  $c_{ui}=1+\alpha\,r_{ui}$; or sample negatives and use a ranking loss such as **BPR**: $-\log\sigma(\hat x_{ui}-\hat x_{uj})$ for a
  positive $i$ and sampled negative $j$.
* **Cold start**: new users/items have no interactions → use content features (text/image/audio embeddings), popularity, or
  onboarding questions; hybrid models combine both.

This is the same low-rank idea as SVD and LoRA (week 4): the interaction matrix is approximately low-rank.

> **Interview angle.** "Why not just use SVD on the rating matrix?" — it's mostly missing, not zero; SVD would treat missing
> entries as zeros. MF fits only observed entries with regularisation.

## D3 · Two-tower retrieval and sampling bias

A **user tower** $f(u)$ and an **item tower** $g(i)$ map features to embeddings; relevance $s(u,i)=f(u)^\top g(i)$. Item embeddings are
precomputed and indexed for ANN search (HNSW, IVF-PQ); only the user tower runs per request.

**Training with in-batch negatives:** for a batch of B positive (user, item) pairs, treat the other items in the batch as negatives
and apply softmax cross-entropy over the B×B score matrix (the same InfoNCE loss as CLIP, week 16).

**Sampling-bias (logQ) correction:** in-batch negatives are sampled proportional to item popularity, so popular items are
over-penalised. Correct the logits: $s'(u,j)=s(u,j)-\log Q(j)$ where $Q(j)$ is item $j$'s sampling probability (estimated from
frequency, e.g. with a streaming count). Mix in uniformly sampled negatives too.

**Practicalities:** temperature, embedding normalisation, hard negatives (but not false negatives), freshness (re-index items often),
feature leakage (don't use features from after the interaction).

> **Interview angle.** Explain why the two-tower model can't use user–item cross features (it would no longer be decomposable for ANN
> search) — that's exactly what the ranking stage is for.

## D4 · Ranking models: feature interactions, DLRM, multi-task learning

**Inputs:** many **sparse categorical** features (user id, item id, category, device…) mapped through **embedding tables**, plus dense
features (counts, recency). Embedding tables dominate model size (billions of rows) — sharded across machines, the main systems
challenge in production recsys.

**Interaction architectures:** logistic regression with manual crosses → **Wide & Deep** (memorisation + generalisation) → **DCN**
(explicit cross layers $x_{l+1}=x_0(w_l^\top x_l)+b_l+x_l$) → **DLRM** (pairwise dot products between embeddings + MLPs) →
transformer/sequence models over the user's history (behaviour sequences, target attention as in DIN).

**Multi-task learning:** predict several objectives (click, like, watch time, share) with shared bottom layers and task-specific
heads. **MMoE** (multi-gate mixture-of-experts) gives each task its own softmax gate over shared experts, reducing negative transfer
between conflicting tasks — conceptually close to your MoE work on speech enhancement. The final score combines task predictions with
tuned weights.

**Calibration** matters because scores feed auctions and combinations — check with reliability diagrams and correct with isotonic or
Platt scaling; down-sampled negatives must be re-weighted.

> **Interview angle.** "Our CTR model's AUC improved but revenue dropped" → calibration changed, objective misalignment, or position/
> selection bias in the logged data; check calibration and run an online test.

## D5 · Systems and pitfalls: bias, feedback loops, exploration, experimentation

* **Position bias:** items shown higher get more clicks regardless of relevance. Correct with inverse propensity weighting (estimate
  examination probability per position via randomisation or click models) or a position feature used in training and fixed at serving.
* **Selection bias and feedback loops:** the model is trained on what the previous model chose to show; popular items get more
  exposure and more data ("rich get richer"). Mitigate with exploration and debiasing.
* **Exploration:** ε-greedy, Thompson sampling or UCB bandits for new items; reserve a small traffic slice.
* **Freshness and real-time features:** streaming feature pipelines (recent clicks), online learning for embeddings of new items.
* **Experimentation:** A/B tests with guardrails, novelty effects, network effects/interference, long-term holdouts, interleaving for
  faster ranking comparisons.
* **Latency:** ~100 ms end to end — caching, ANN tuning, model distillation for ranking, feature-store lookups.
* **On-device recommendation** (relevant to you): small models on phones/cars for privacy (e.g. suggested destinations, media),
  trained with federated learning or using on-device personalisation layers on top of a global model.

> **Interview angle.** Always mention the feedback loop and how you'd evaluate without being fooled by it: randomised traffic,
> counterfactual evaluation with propensities, long-term holdouts.

## Questions

??* d1 [recsys] | Why are recommender systems built as multi-stage funnels?
Scoring every item with a rich model is too slow at millions of items and ~100 ms budgets. Cheap retrieval (two-tower + ANN, co-visitation,
heuristics) narrows millions to hundreds or thousands with high recall; a heavier ranking model with cross features scores those precisely;
a re-ranking stage applies diversity, freshness and business rules. Each stage optimises a different objective and latency budget.

??* d2 [recsys] | How does matrix factorisation handle the missing entries of a rating matrix, and how do you adapt it to implicit feedback?
It fits only observed entries, minimising squared error plus L2 regularisation of the latent factors (and biases), via SGD or ALS — unlike plain
SVD, which would treat missing as zero. For implicit feedback, either treat every pair as a 0/1 preference weighted by confidence that grows with
interaction strength (weighted ALS), or sample negatives and optimise a pairwise ranking loss such as BPR.

??* d3 [recsys] | What is the logQ correction in two-tower retrieval training?
With in-batch negatives, items appear as negatives in proportion to their popularity, so the softmax over-penalises popular items and biases the
model. Subtracting log Q(j) — the log sampling probability of item j — from each logit corrects the sampled softmax toward the full softmax over all
items. Q is estimated from item frequencies (often with streaming counts).

?? d3 [recsys] | Why can't the retrieval model use user–item cross features?
Retrieval relies on the score decomposing as a dot product f(u)·g(i) so item embeddings can be precomputed and searched with approximate nearest
neighbours. Cross features depend on both user and item and would require scoring every pair at request time. They belong in the ranking stage,
which only sees the retrieved candidates.

??* d4 [recsys, moe] | What is MMoE and why is it used for multi-task ranking?
Multi-gate Mixture-of-Experts: a set of shared expert networks plus one softmax gate per task that mixes the experts' outputs into that task's tower.
Tasks such as click, watch time and share partly conflict; a fully shared bottom causes negative transfer, while separate models waste data. Per-task
gates let each task use a different combination of shared experts, improving multi-task performance.

??* d5 [recsys, bias] | What is position bias in logged recommendation data and how do you correct it?
Users examine and click higher positions more, independent of relevance, so logged clicks over-credit top-ranked items. Estimate the probability that
each position is examined (from randomised experiments or click models) and weight training examples by its inverse (inverse propensity scoring), or
train with position as a feature and set it to a fixed value at serving time.
