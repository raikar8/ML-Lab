## D1 · The GIL, threads, processes and asyncio

**First, the misconception.** "Python can't do multithreading" is wrong. `threading.Thread` creates real
operating-system threads, scheduled by the OS. What CPython restricts is **parallel execution of Python
bytecode**. The **Global Interpreter Lock (GIL)** is a mutex that a thread must hold to run Python bytecode, so in
the default build only one thread executes Python code at a time, even on a 16-core machine.

**Why it exists.** CPython manages memory by **reference counting**: every object has a counter that is
incremented and decremented constantly. Making each of those updates atomic, or putting a lock on every object,
would slow single-threaded code and complicate the C API. One big lock made the interpreter and thousands of C
extensions simple and fast in the single-threaded case. That trade-off made sense in the 1990s and became a
bottleneck in the multi-core era.

**When the GIL is released:**

* during **blocking I/O** (file reads, sockets, `time.sleep`), so other threads run while one waits;
* inside **C extensions that release it explicitly**. NumPy (large array operations), PyTorch (kernels and CUDA
  calls), hashlib and zlib all drop the GIL during heavy work, so threads calling them *can* run in parallel;
* periodically, for fairness: a running thread is asked to drop it every *switch interval*
  (`sys.getswitchinterval()`, 5 ms by default).

**So which tool when?**

| Workload | Use | Why |
|---|---|---|
| I/O-bound (HTTP, disk, DB, many sockets) | `threading` / `ThreadPoolExecutor` | the GIL is released while waiting |
| Very many concurrent I/O tasks (10k connections) | `asyncio` | one thread, cooperative tasks, tiny per-task cost |
| CPU-bound pure Python (parsing, feature extraction, augmentation) | `multiprocessing` / `ProcessPoolExecutor` | separate interpreters, each with its own GIL |
| CPU-bound but inside NumPy/PyTorch kernels | threads are fine | the kernels release the GIL |
| Heavy numeric loops | vectorise, Numba, Cython, C++ extension | often 10–100× faster than any parallelism |

**Processes have costs.** Each worker is a separate interpreter with its own memory. Arguments and results are
**pickled** and sent over pipes, so passing large arrays back and forth can cost more than the work itself (use
shared memory, `torch.multiprocessing` shared tensors, or memory-mapped files). Functions you send must be
picklable: top-level functions work; lambdas and nested functions don't. Start methods differ: *fork* copies the
parent quickly but is unsafe with threads (and with CUDA initialised); *spawn* starts a fresh interpreter, which
is slower but safe. Python 3.14 made *forkserver* the default on Linux. This is exactly why PyTorch's
`DataLoader(num_workers>0)` uses worker **processes** (augmentation is Python-heavy) and why you must create CUDA
contexts inside workers carefully, or not at all.

**The GIL does not make your code thread-safe.** `counter += 1` compiles to several bytecodes (load, add, store);
a thread switch between them loses updates. Protect shared mutable state with `threading.Lock`, or better,
**don't share**: pass messages through `queue.Queue` (thread-safe), give each worker its own data, and combine
results at the end.

```python
import queue, threading
q, results = queue.Queue(maxsize=64), []
lock = threading.Lock()

def worker():
    while (item := q.get()) is not None:     # None is the shutdown sentinel
        out = process(item)
        with lock:
            results.append(out)
```

**asyncio in one paragraph.** One thread runs an event loop. Coroutines (`async def`) `await` I/O and give control
back to the loop while they wait, so thousands of network calls can overlap with almost no overhead. It is
**cooperative**: one blocking call (`time.sleep`, a CPU-heavy function, a synchronous HTTP library) freezes every
task. Push blocking work to a thread with `await asyncio.to_thread(fn, ...)`. Use asyncio for model-serving
front ends and crawlers, not for CPU work.

**The future: free-threaded Python.** PEP 703 added a CPython build without the GIL. It was experimental in 3.13
and became **officially supported (but optional) in 3.14**, shipped as a separate interpreter (`python3.14t`);
the default build still has the GIL. In the free-threaded build, threads run Python bytecode in parallel on all
cores. The costs are some single-threaded overhead and extra memory per object, and C extensions must be rebuilt
and declare support (otherwise the GIL is turned back on at import). Check `sys._is_gil_enabled()`. Python 3.14
also added **sub-interpreters** (`concurrent.interpreters`, `InterpreterPoolExecutor`): isolated interpreters in one
process, each with its own GIL. For interviews: explain the GIL, say *why* it exists, give the decision table
above, and mention that free threading is now supported but opt-in, with an ecosystem still catching up.

> **Interview angle.** "Why doesn't my threaded feature extractor get faster?" (CPU-bound Python + GIL → use
> processes or vectorise.) "Why is the DataLoader using processes?" "Is `x += 1` thread-safe in CPython?" (No.)
> "When would asyncio beat threads?" (Thousands of mostly idle I/O tasks.)

## D2 · Python's object and memory model

**Everything is an object; names are references.** `a = b` binds another name to the same object. `is` compares
identity, `==` compares values (via `__eq__`). Mutability decides whether "changing" an object is visible through
every name. That's the root of the aliasing bugs in Week 0.

**Memory management.** CPython frees an object the moment its reference count hits zero (deterministic, so
`with` blocks and `del` of the last reference release resources promptly). Reference **cycles** (a ↔ b) never reach
zero, so a generational **cyclic garbage collector** periodically finds and frees unreachable cycles (`gc` module).
Practical consequences for ML: a stray reference to a tensor (in a list of losses, an exception traceback, a
closure) keeps GPU memory alive. Log `loss.item()`, not `loss`. `weakref` lets caches refer to objects without
keeping them alive.

**How `obj.attr` is resolved** (worth knowing precisely):

1. **data descriptors** on the type (objects defining `__set__` or `__delete__`, e.g. `property`, `__slots__` entries);
2. the instance's `__dict__`;
3. **non-data descriptors** and plain class attributes (functions become bound methods here);
4. `__getattr__`, if defined, as the last resort.

**Descriptors** are how `property`, `classmethod`, `staticmethod`, bound methods and ORM/config fields work: an
object in the class with `__get__`/`__set__` controls access to the attribute. `__set_name__` tells it which name
it was assigned to. `functools.cached_property` is a *non-data* descriptor: on first access it stores the value in
the instance `__dict__`, which then shadows it.

**Classes are objects too.** `type` builds them; `__init_subclass__` runs when a subclass is defined (perfect for
plug-in registries); metaclasses customise class creation, but you rarely need one.
**MRO and `super()`.** With multiple inheritance, Python linearises the base classes with the C3 algorithm
(`Cls.__mro__`). `super()` means "the next class in the MRO", not "my parent", which is why cooperative
`super().__init__(**kwargs)` chains work in mixins and why inconsistent hierarchies raise `TypeError`.

**Special methods define behaviour.** `__repr__` (for debugging; make it unambiguous), `__eq__` plus `__hash__` (equal
objects must hash equally; mutable objects usually shouldn't be hashable), `__len__`, `__iter__`, `__getitem__`,
`__call__`, `__enter__`/`__exit__`, arithmetic (`__add__`, `__radd__`, `__matmul__`). Return `NotImplemented` (not
`False`) from a binary operator for unknown types so Python can try the reflected method.

**Memory per object.** A plain instance carries a `__dict__`. `__slots__ = ("x", "y")` removes it, saving memory
for millions of small objects and catching typos in attribute names. `@dataclass(slots=True, frozen=True)` gives
you that plus immutability.

> **Interview angle.** "What's the difference between `is` and `==`?" "Why can a list be a dict key? (It
> can't — why?)" "What happens when you access a method on an instance?" (A function is a non-data descriptor;
> `__get__` returns a bound method.) "Why might GPU memory grow during training even though tensors go out of
> scope?"

## D3 · Object-oriented design done well

**Why OOP at all?** Objects bundle **state with the operations that keep that state valid**. The benefits are
real when there *is* state with invariants (a ring buffer with read/write indices, a model with parameters, a
connection pool) and when you need **polymorphism**: many implementations behind one interface (several feature
extractors, model backends, loss functions). Without state or variation, a function is better. A class with one
method and an `__init__` is usually a function in disguise.

**The ideas that matter:**

* **Encapsulation**: callers use a small public interface; internals (`_leading_underscore`) can change. Protect
  invariants in one place, e.g. a `RingBuffer` never lets `head` exceed capacity. Python trusts you (no `private`),
  so convention and `@property` do the work.
* **Abstraction**: expose *what*, hide *how*: `extractor.features(audio)` and not the FFT details.
* **Polymorphism**: code written against an interface works with any implementation. In Python this is mostly
  **duck typing**: if it has `.process(frame)`, it's a stage.
* **Inheritance**: reuse plus an "is-a" relationship. Useful but over-used.

**Composition over inheritance.** Deep hierarchies (`BaseModel → AudioModel → StreamingAudioModel →
QuantizedStreamingAudioModel`) multiply classes for every combination of features and couple everything to the
base class. Compose instead: a `StreamingRunner` *has* a model, a `Quantizer` *wraps* a layer, a `Pipeline` *has* a
list of stages. You can then mix features freely, swap parts in tests and keep each class small.
**Inherit** when the subclass is genuinely substitutable for the parent (see Liskov, D4) and the base class was
designed for extension (`nn.Module`, `Dataset`, an ABC). **Compose** for everything else.

**Interfaces in Python: ABCs vs Protocols.**

```python
from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable

class FeatureExtractor(ABC):            # nominal: implementers must inherit
    @abstractmethod
    def __call__(self, audio): ...

@runtime_checkable
class Stage(Protocol):                  # structural: anything with these methods qualifies
    def process(self, frame): ...
    def reset(self) -> None: ...
```

Use an **ABC** when you own the hierarchy and want instantiation of incomplete classes to fail early and shared
default behaviour. Use a **Protocol** (PEP 544, static duck typing) to describe what you *need* from collaborators,
including third-party classes you can't modify; type checkers verify it without inheritance.

**Data classes for data.** `@dataclass(frozen=True)` for configs, results and messages: generated `__init__`,
`__repr__` and `__eq__`, immutability, and easy serialisation. Keep behaviour that belongs with the data, but don't
turn every dict into a class hierarchy.

**Common OOP smells:** god classes (a `Trainer` doing data loading, logging, checkpointing and evaluation);
inheritance used only to reuse a helper; `isinstance` chains instead of polymorphism; getters and setters for
everything (use plain attributes, add `@property` later without breaking callers); mutable shared class
attributes (`class A: cache = {}` is shared by every instance).

> **Interview angle.** "When would you use inheritance vs composition? Give an example from your code." "ABC or
> Protocol for a plug-in interface?" "Refactor this 400-line class." (Find the responsibilities, extract
> collaborators, inject them.)

## D4 · SOLID and the design patterns ML code actually uses

**SOLID, with Python examples.**

* **S — single responsibility.** A class has one reason to change. Split `Trainer` into the training loop, a
  `CheckpointManager`, a `MetricsLogger` and an `Evaluator`.
* **O — open/closed.** Add behaviour without editing tested code. Register a new loss in a registry or pass in a
  new callback, rather than adding another `elif loss == "focal":` branch.
* **L — Liskov substitution.** A subclass must work wherever its parent does: same preconditions or weaker,
  postconditions the same or stronger. A `StreamingModel` whose `forward` suddenly needs an extra `state`
  argument is *not* a substitutable `Model`, so make it a different interface.
* **I — interface segregation.** Small, focused interfaces. A `Stage` needs `process` and `reset`, not
  `export_onnx`, `plot` and `save`.
* **D — dependency inversion.** High-level code depends on abstractions; concrete pieces are **injected**.
  `Trainer(model, optimizer, logger)` instead of creating a W&B logger inside, so tests can pass a fake logger and
  production can swap backends.

**The patterns you'll actually meet:**

| Pattern | ML example | Python form |
|---|---|---|
| **Strategy** | interchangeable losses, optimisers, samplers, decoding (greedy/beam) | pass a callable or an object with a known method |
| **Factory / Registry** | `build_model("conformer", **cfg)`, timm/HF model zoos | dict name → class, filled by a `@register("name")` decorator or `__init_subclass__` |
| **Template method** | `nn.Module.__call__` runs hooks around your `forward`; Lightning's `training_step` | base class defines the skeleton, subclasses fill in steps |
| **Observer / callbacks** | early stopping, checkpointing, LR schedulers, logging hooks | `trainer.add_callback(cb)`; trainer calls `cb.on_epoch_end(state)` |
| **Adapter** | wrapping ONNX Runtime / TFLite / ExecuTorch behind one `Backend.run(x)` interface | a thin class translating one API into another |
| **Decorator (wrapper object)** | `QuantizedLinear(linear)`, `LoRA(linear)`, caching or retry wrappers | an object that holds and forwards to another with the same interface |
| **Composite** | `nn.Sequential`, an audio `Pipeline` of `Stage`s that is itself a `Stage` | a container implementing the same interface as its parts |
| **Context manager** | `torch.no_grad()`, timers, temporary eval mode, file and lock handling | `with` + `__enter__`/`__exit__` or `@contextmanager` |

**When patterns hurt.** Every abstraction is a cost to read. YAGNI ("you aren't gonna need it") and the rule of
three (abstract on the third duplicate, not the first) apply. A registry for two models, or an abstract factory for
one backend, is over-engineering. Interviewers like to hear *why not* as much as *why*.

> **Interview angle.** "Design the plug-in system for model backends on device (TFLite, ONNX, a vendor NPU)."
> (Adapter + registry + a small Protocol; the selection logic depends only on the Protocol.) "Which SOLID
> principle does an `if model_type == …` chain violate?" (Open/closed.)

## D5 · Engineering practice: tests, types, logging, config, structure

**Tests (pytest).** Test behaviour, not implementation. Use plain `assert`s; `@pytest.mark.parametrize` for tables
of cases; **fixtures** for shared setup (temporary directories via `tmp_path`, small models, seeded RNGs);
`pytest.raises` for errors; `monkeypatch` to replace time, network or environment. For ML code, add:

* **shape and dtype tests** for every module;
* **determinism**: same seed, same output (and know which CUDA ops are non-deterministic);
* **numerical checks** against a reference (a NumPy implementation, finite-difference gradients) with explicit
  tolerances (`torch.testing.assert_close`);
* **overfit one batch**: the loss must go to about 0, the cheapest end-to-end smoke test there is;
* **property-based tests** (Hypothesis) for invariants, such as decode(encode(x)) == x and a softmax row summing to 1;
* **golden files** for exported models: the same input gives the same output within tolerance after export.

**Design for testability.** Inject dependencies (clock, RNG, file system, network client) rather than reaching for
globals, so tests can pass fakes. A function that calls `time.sleep` directly is hard to test; one that takes
`sleep=time.sleep` is easy.

**Types.** Annotate public functions and dataclasses; run `mypy` or `pyright` in CI. Types are documentation the
tools can check, and they catch the `None`-return and wrong-argument-order bugs that unit tests miss. Use
`Protocol` for duck-typed parameters and `TypedDict`/dataclasses instead of loose dicts.

**Errors.** Validate inputs at the boundary (config loading, API handlers) and fail fast with a message that says
what was wrong and how to fix it. Catch the narrowest exception, never a bare `except:`, and re-raise with context
(`raise ConfigError(...) from err`). Don't use exceptions for normal control flow in hot loops.

**Logging, not print.** `logger = logging.getLogger(__name__)` per module; configure handlers once at the entry
point; use levels (`debug` for tensors' shapes, `info` for progress, `warning` for recoverable issues). Use
structured key=value logs for anything a machine will parse. Log configuration and versions at start-up for
reproducibility.

**Configuration.** One typed, validated config object (frozen dataclass or pydantic) loaded from YAML/CLI;
reject unknown keys (typos silently ignored are a classic multi-day bug); keep defaults in code; save the resolved
config next to every checkpoint.

**Structure and tooling.** `src/` layout with a `pyproject.toml`; small modules with clear names; no work at import
time; a `__main__` or CLI entry point. Run `ruff` (lint + format) and the type checker in **pre-commit** and CI;
pin dependencies for applications (lock files), use ranges for libraries.

**What reviewers look for:** clear names; small functions; no duplicated logic; errors handled at the right
level; tests for the change, including an edge case; no hidden global state; complexity appropriate to the problem;
docstrings saying *why* rather than *what*; and a PR description that says what changed, why, and how it was
tested.

> **Interview angle.** "How do you test ML code?" (Shapes, determinism, reference comparisons, overfit a batch,
> golden outputs, plus the usual unit tests.) "Your colleague's training run silently used the wrong learning
> rate. What process change prevents it?" (Validated config that rejects unknown keys; log the resolved config;
> a test for config loading.)

## Questions

??* d1 [python, gil, concurrency] | Is multithreading possible in Python? What exactly does the GIL prevent?
Yes. Python threads are real OS threads. In the default CPython build, the GIL lets only one thread execute
Python **bytecode** at a time, so CPU-bound pure-Python code doesn't speed up with threads. The GIL is released
during blocking I/O and by C extensions such as NumPy and PyTorch while they compute, so I/O-bound work and
library-heavy work do run concurrently. Since Python 3.14 there is also an officially supported (opt-in)
free-threaded build, `python3.14t`, with no GIL.

??* d1 [python, gil] | Why does CPython have a GIL at all?
Memory is managed by reference counting, and the counts change on almost every operation. Without a global lock
each change would need atomic operations or per-object locks, slowing single-threaded code and complicating the C
API and thousands of extensions. One lock kept the interpreter simple, fast in the common case, and made C
extensions easy to write. Free-threaded CPython (PEP 703) replaces it with biased and deferred reference counting,
per-object locks and a thread-safe allocator. The price is some single-threaded overhead and extra memory.

??* d1 [concurrency, decision] | Threads, processes or asyncio — how do you choose?
**I/O-bound** with moderate concurrency → threads (`ThreadPoolExecutor`). **Huge numbers of concurrent I/O tasks**
→ asyncio (one thread, cooperative). **CPU-bound pure Python** → processes (`ProcessPoolExecutor`), minding pickling
costs and start methods. **CPU-bound inside NumPy/PyTorch** → threads are fine, or just vectorise. For heavy
numeric loops, first make the work itself faster (vectorise, Numba, a C++ extension) before parallelising.

?? d1 [concurrency, thread-safety] | Is `counter += 1` thread-safe in CPython? How do you make shared updates safe?
No. It is several bytecodes (load, add, store), and a thread switch in between loses updates; the GIL only
protects the interpreter's own state, not your invariants. Use a `threading.Lock` around the update, use
`queue.Queue` to pass work and results between threads, or avoid shared state entirely (each worker returns its
results and you combine them at the end).

?? d1 [multiprocessing, pytorch] | What are the costs and gotchas of multiprocessing for data pipelines?
Each process has its own memory; arguments and results are pickled through pipes, so moving big arrays can cost
more than the computation (use shared memory or memory-mapped files). Functions must be picklable (no lambdas or
closures). *fork* is fast but unsafe with threads and an initialised CUDA context; *spawn* and *forkserver* are
safe but slower to start (Python 3.14 made forkserver the default on Linux). Seed each worker separately, or
augmentations repeat across workers. Guard the entry point with `if __name__ == "__main__":`.

?? d1 [asyncio] | What happens if you call `time.sleep(1)` inside an asyncio coroutine?
The whole event loop blocks for a second: every other task stops, because asyncio is cooperative and
`time.sleep` never yields. Use `await asyncio.sleep(1)`, and push blocking or CPU-heavy calls to a thread with
`await asyncio.to_thread(fn, ...)` (or to a process pool via `loop.run_in_executor`).

??* d2 [python, object-model] | Explain `is` vs `==`, and why `a = b` doesn't copy.
Names are references to objects. `a = b` makes `a` refer to the same object, so mutating it through either name
is visible through both. `is` checks identity (the same object), `==` calls `__eq__` (equal values). Use `is` only
for singletons (`None`, sentinels). Small integers and some strings are cached, so `is` sometimes "works" on
them by accident, which is why it must not be used for value comparison.

?? d2 [python, memory] | How does CPython free memory, and why can GPU memory keep growing in a training loop?
Reference counting frees an object as soon as its count reaches zero; a cyclic garbage collector periodically
collects unreachable reference cycles. GPU memory grows if something keeps tensors alive: appending `loss` (which
holds the whole autograd graph) instead of `loss.item()` to a list, storing outputs in a cache, holding an
exception traceback, or closures capturing tensors. The caching allocator also keeps freed blocks reserved for
reuse, so `nvidia-smi` overstates live usage.

?? d2 [python, descriptors] | What is a descriptor, and where do you use them without noticing?
An object in a class that defines `__get__` (and possibly `__set__`/`__delete__`), which controls access to the
attribute of that name. Functions are non-data descriptors (so `obj.method` returns a bound method); `property`,
`classmethod`, `staticmethod`, `functools.cached_property`, `__slots__` fields, dataclass-like field validators and
ORM columns are all descriptors. Data descriptors take precedence over the instance `__dict__`; non-data ones
don't, which is how `cached_property` stores its value and then gets out of the way.

?? d2 [python, inheritance] | What does `super()` do with multiple inheritance?
It returns a proxy to the **next class in the method resolution order** of the instance's type (C3
linearisation, `Cls.__mro__`), not the literal parent. That makes cooperative mixins work if every class calls
`super().__init__(**kwargs)` and passes on the arguments it doesn't use. Hierarchies with no consistent
linearisation raise `TypeError` at class creation.

??* d3 [oop, design] | Why is object-oriented programming useful, and when is it the wrong tool?
It bundles state with the operations that keep that state valid (encapsulation), lets callers depend on an
interface instead of an implementation (polymorphism), and lets you swap implementations (backends, losses,
feature extractors) without touching callers. It's the wrong tool when there's no state or variation: a class
with only `__init__` and one method should be a function, and plain data is better as a dataclass or dict. Deep
hierarchies built only for code reuse are a smell.

??* d3 [oop, composition] | Composition vs inheritance — when do you use each? Give an ML example.
Inherit when the subclass is truly substitutable for the parent and the parent is designed for extension
(`nn.Module`, `Dataset`, an ABC). Compose for everything else: a `StreamingRunner` *has* a model and a state
buffer; `QuantizedLinear` *wraps* a `Linear`; a `Pipeline` *has* stages. Composition avoids a class explosion
(every combination of features), keeps classes small, and lets you inject fakes in tests.

?? d3 [oop, interfaces] | ABC or Protocol for a plug-in interface?
An **ABC** is nominal: implementations must inherit; instantiating a class with missing abstract methods fails
early, and the base can provide shared behaviour. A **Protocol** is structural (static duck typing): anything with
the right methods type-checks, including third-party classes you can't modify, with no inheritance needed. Use a
Protocol to describe what your code *needs* from collaborators, and an ABC when you own the hierarchy and want
enforced structure plus defaults.

?? d3 [oop, smells] | Name four OOP smells you'd flag in a code review.
A god class with many responsibilities (a trainer that also loads data, logs, checkpoints and evaluates).
Inheritance used just to reuse a helper. `isinstance`/`type ==` chains instead of polymorphism. Mutable class
attributes shared by every instance (`cache = {}` at class level). Others: getters and setters for every field,
and long parameter lists that should be a config object.

??* d4 [solid] | Explain SOLID with one ML example per letter.
**S**: split a `Trainer` that also checkpoints and logs into collaborators. **O**: add a loss through a registry
instead of another `elif`. **L**: a `StreamingModel` needing an extra state argument isn't a drop-in `Model`, so
give it its own interface. **I**: a `Stage` interface with `process` and `reset`, not `export` and `plot` as well.
**D**: inject the logger, optimiser and data source into the trainer so tests use fakes and production can swap
backends.

?? d4 [patterns] | Which design patterns show up in PyTorch / training code?
Template method (`nn.Module.__call__` wraps your `forward` with hooks; Lightning's step methods). Composite
(`nn.Sequential`, `ModuleList`). Strategy (losses, optimisers, samplers, schedulers as swappable objects).
Observer (callbacks and hooks). Factory/registry (model zoos, `build_model(name)`). Decorator objects (LoRA or
quantisation wrappers around a layer). Context manager (`no_grad`, `autocast`). Adapter (one interface over
ONNX/TFLite/ExecuTorch runtimes).

?? d4 [patterns, judgement] | When is adding a design pattern a mistake?
When it adds indirection without solving a present problem: a registry for two classes, an abstract factory for
one backend, interfaces nobody else implements. Apply YAGNI and the rule of three: abstract when the third variant
appears, and keep it easy to inline later. Interviewers value the reasoning about trade-offs (readability,
testability, extension points) more than naming the pattern.

??* d5 [testing, ml] | How do you test ML code beyond unit tests?
Shape and dtype tests for every module; determinism with fixed seeds; numerical comparisons against a reference
implementation or finite-difference gradients with explicit tolerances; overfitting a single batch (the loss should
approach 0); property-based tests for invariants (round-trips, a softmax row summing to 1, monotonic metrics);
golden-output tests for exported or quantised models; and data tests (schema, ranges, label distribution, no
train/test overlap).

?? d5 [engineering, config] | A training run silently used the wrong learning rate because of a typo in the YAML. How do you prevent it?
Load config into a typed, frozen dataclass (or pydantic model) that **rejects unknown keys** and validates ranges;
fail at start-up with a message listing every problem. Log the fully resolved config, save it next to every
checkpoint, and test config loading in CI. Prefer one source of truth for defaults (in code) over defaults
scattered across scripts.

?? d5 [engineering, testability] | Why is "inject your dependencies" good advice, and what does it look like in Python?
Code that creates its own clock, RNG, file system or network client is hard to test and hard to reconfigure.
Pass them in as parameters with sensible defaults (`def retry(fn, sleep=time.sleep)`, `Trainer(model, logger)`), so
tests pass fakes (an instant sleep, an in-memory logger, a seeded RNG) and production can swap implementations. It
is dependency inversion at small scale, with no framework needed.

?? d5 [engineering, review] | What do you look for when reviewing a pull request?
Correctness first (edge cases, error handling, concurrency, numerical stability), then tests that cover the change
including an edge case, then clarity (names, small functions, no duplication, no hidden global state), then fit
with the codebase's patterns and appropriate complexity. Check performance on hot paths, the security of inputs
and secrets, and a description that says what changed, why, and how it was tested. Comment on the code, not the
person, and separate must-fix from nice-to-have.
